# 400字画像圧縮ツール

写真を **コメント1行（400字以内）** に収まる文字列に変換するツールです。DCInsideのコメントのように文字数が短く、画像を投稿できない場所で写真をやり取りするために使います。受け取った人はその文字列をこのページに貼り付けるか、リンクを開いて写真を見ます。

- `index.html` 1ファイルで動作し、すべての処理はブラウザ内で完結します。サーバーもアップロードもありません。
- 結果はぼやけたプレビュー程度です。400字に入る情報は300〜650バイトしかないため、形・色・雰囲気がわかる程度に圧縮されます。

## 使い方

1. **만들기（作成）** タブに写真をドラッグするか、クリックして選ぶか、Ctrl/⌘+V で貼り付けます。
2. **복사（コピー）** を押すと、`https://g.yeon.at/?뗈앏괟샡…` のような400字以内の1行がコピーされます。そのままコメントに貼り付けます。
3. 受け取った人はその行をブラウザのアドレスバーに貼り付ければ、すぐに写真が見られます。**보기（表示）** タブに貼り付けても構いません。前後に別の文章が混ざっていてもコード部分だけを読み取ります。

`https://g.yeon.at/?コード` と `https://g.yeon.at/index.html?コード` のどちらでも動きます。

## 設定

| 項目 | 説明 |
|---|---|
| コード文字：ハングル | 1文字に13ビット。アドレスを付けるとコードに381字、約619バイト入ります。最も鮮明です。 |
| コード文字：英字 | 英数字と `-`・`_` のみで、1文字に6ビット。ハングルが使えない場所向けです。 |
| 前に付けるアドレス | 既定値は `https://g.yeon.at/?`（19字）。`https://` で始めることでコメント内でクリックできるリンクになります。この分だけ写真に使える文字が減ります。空にするとコードだけを出力します。 |
| 文字数制限 | 既定値は400（DCInsideのコメント）です。 |

## 仕組み

1. 写真を長辺64ピクセルのグリッドに縮小し、YCbCr色空間に変換します。文字数に余裕があればグリッドを96〜512ピクセルに広げます。
2. 画像全体に2次元DCTをかけ、低い周波数から順に並べます。
3. 高い周波数ほど、また色（色差）成分ほど粗く量子化します。
4. 結果をコンテキスト適応型の二値算術符号化（LZMA式レンジコーダー）で圧縮します。
5. 文字数制限に収まる最も細かい量子化段階を二分探索で見つけ、復号結果が変わらない限り末尾の文字を削ります。
6. 表示側はコサイン級数を画面解像度で直接計算するため、拡大してもブロック状にならず滑らかです。

## JPG data リンクタブ

`data:` リンクをそのまま画像として表示する場所（HTMLやMarkdownの画像を使える場所）では、通常のJPGを `data:` リンクにして使えます。同じ文字数なら、このページのコードのほうが鮮明です（1200×1200の絵を7,000字で：JPG 25.6dB、ハングルコード 28.0dB）。JPGはファイルヘッダーだけで数百字あるため、400字には収まりません。

## 補足

- DCInside のコメントは画像や `data:` リンクを表示しないため、受け取った人がこのページを直接開く必要があります。
- ハングルコードは `가`（U+AC00）から始まる8,192個の完成形ハングル音節を使います。文字数ではなくバイト数で制限するサイトでは英字コードを使ってください。

### 概要

DCInside のコメントは400字までしか書けず、画像を投稿できず、`data:` リンクも画像として表示しません。通常のJPGを `data:` リンクにすると、ファイルヘッダーだけで約800字になるため、400字には入りません。

このページは、写真を約300〜620バイトに縮める専用の圧縮方式を使います。その結果をハングル音節か英数字で書き表してコメント1行に収め、受け取った人はリンクを開くかコードを貼り付けて写真を見ます。

- アドレス：https://g.yeon.at/
- このリポジトリには公開用ファイル（`index.html`、`CNAME`、README）だけがあります。ソースとテスト資料は [Velvitty/img-dev](https://github.com/Velvitty/img-dev) にあります。

### 画面構成

ページにはタブが3つあります。

#### 作成（만들기）

1. 写真をドラッグするか、枠をクリックして選ぶか、Ctrl/⌘+V で貼り付けます。複数枚まとめて入れられます。
2. 写真ごとにカードができます。左が元画像、右が受け取った人に見える写真です。
3. カード下の数字の意味は次のとおりです。

   | 表示 | 意味 |
   |---|---|
   | 원본（元画像） | 元のファイルサイズ |
   | 코드（コード） | 写真を入れた文字数（アドレスを除く） |
   | 전체（全体） | アドレスを含む文字数と上限。上限内なら緑色です。 |
   | 압축 단계（圧縮段階） | 0〜127。小さいほど細かく圧縮されています。 |
   | 격자（グリッド） | 写真を記録した大きさ。400字なら64px、文字数が多いほど大きくなります（最大512px）。 |

4. ボタンは3つです。
   - **복사（コピー）：** アドレスとコードを1行でコピーします。コピーが使えない環境では文字列を選択しておくので、Ctrl/⌘+C を押してください。
   - **보기 탭에서 확인（表示タブで確認）：** 受け取る側の画面を確認します。
   - **삭제（削除）：** カードを消します。

設定（コード文字、文字数制限、前に付けるアドレス）を変えると、入れてある写真がすべて圧縮し直されます。最初に開くと夕焼けの例が1枚入っていて、`예시（例）` の印が付きます。

#### 表示（보기）

受け取ったコードやリンクを貼り付けると写真が表示されます。

- 前後に別の文章が混ざっていてもコード部分だけを読み取ります。ハングルコードは4字以上続く最も長い部分、英字コードは最後の `?` か `#` の後ろで最も長い部分を選びます。
- 写真の下に、コードの文字数、コードの種類、圧縮段階が表示されます。
- コードが途切れていたり、コードでない文字列だったりすると、その旨を表示します。

リンク（`https://g.yeon.at/?コード`）から来ると、このタブがすぐに開きます。

#### JPG data リンク

文字数制限に余裕がある場所で使うツールです。写真をJPGで圧縮し直し、`data:image/jpeg;base64,…` リンクにします。

| 設定 | 説明 |
|---|---|
| 目標リンク長 | 長さに収まる最も高い品質を探します。品質が35を下回りそうなときだけ画像を縮小します。YouTube・Reddit（9,900）、Instagram（2,150）、GitHub（65,000）のボタンがあり、囲むタグのために少し余裕を残した値です。 |
| 品質指定 | 選んだ品質（5〜95）で1回だけ圧縮します。 |
| 長辺の最大サイズ | 元のまま、1920、1280、800、480ピクセルから選びます。 |

結果はリンク、`<img>` タグ、Markdown 形式でコピーできます。

### コードとリンクの形式

| 形式 | 例 | コードに使える文字 | 入る量 |
|---|---|---|---|
| ハングル + アドレス（既定） | `https://g.yeon.at/?뗈앏괟…` | 381字 | 約619バイト |
| 英字 + アドレス | `https://g.yeon.at/?TqVTweO…` | 381字 | 約285バイト |
| ハングルコードのみ | `뗈앏괟…` | 400字 | 650バイト |
| 英字コードのみ | `TqVTweO…` | 400字 | 300バイト |

- **ハングルコード：** 1文字に13ビット入り、英字の約2.2倍です。`가`（U+AC00）から `쯿`（U+CBFF）までの8,192字を使います。
- **英字コード：** `A–Z a–z 0–9 - _` だけを使います。ハングルが使えない場所や、文字数をバイトで数える場所で使います。
- **`https://` を付ける理由：** DCInside のコメントは `https://` で始まらないとクリックできるリンクになりません。
- **アドレス内のハングル：** アドレスバーにはハングルで表示されますが、ブラウザは1音節を `%EB%97%88` のような9文字にして送ります。381音節で約3.4KBになり、URL長の上限よりずっと短いです。
- **`#` 形式：** `https://g.yeon.at/#コード` でも開きます。アドレスが約7KBを超えるほどコードが長い場合（ハングルで約770字以上）、コピー時に自動で `?` の代わりに `#` を使います。`?` 以降はサーバーに送られ、GitHub Pages は8KBを超えるアドレスを拒否するためです（414エラー）。

### 画質と文字数

写真8枚を `https://g.yeon.at/?` の後ろの381字に圧縮して測った結果です。PSNRは元画像にどれだけ近いかを表す値で、高いほど元画像に近くなります（[PSNRの読み方](#psnrの読み方) を参照）。

| 写真 | 英字コード | ハングルコード |
|---|---|---|
| ベッドの上のパグ | 25.8 dB | 28.0 dB |
| 霧の山と人 | 26.5 dB | 27.6 dB |
| 野原の人 | 24.7 dB | 26.7 dB |
| クマ | 24.2 dB | 26.3 dB |
| セイウチ | 22.6 dB | 23.9 dB |
| 毛布にくるまったパグ（森） | 21.9 dB | 23.1 dB |
| フィヨルドと崖 | 21.1 dB | 22.4 dB |
| 木の床の上の黒い子犬 | 20.8 dB | 22.0 dB |
| **平均** | **23.4 dB** | **25.0 dB** |

向いている写真と向いていない写真がはっきり分かれます。

- **向いている写真：** 大きな塊となめらかな色の変化が中心の写真です。霧、空、近くで撮った顔や動物などです。
- **向いていない写真：** 木目、草むら、岩のように細かい模様が画面いっぱいに広がる写真です。模様に文字を使い切ってもぼやけたままです。
- **先に切り抜く：** 見せたい部分だけを残すと、同じ文字数でずっと鮮明になります。
- **文字：** 400字では文字は読めません。
- **文字数制限を増やすと：** 写真を入れるグリッドが大きくなり、より鮮明になります。1200×1200の絵を512×512で測ると、400字は64pxのグリッドで21.6dB、1,367字は96pxで24.0dB、4,000字は192pxで26.6dB、7,000字は384pxで28.0dBでした。グリッドは最大512pxなので、約1万字を超えるとほとんど良くなりません。

### プライバシーと動作環境

- **アップロードなし：** 写真はブラウザの外に出ません。圧縮も復元もページ内のスクリプトが行います。
- **コードが写真そのもの：** サーバーには何も保存されないので、コードを持っている人なら誰でも同じ写真を見られます。コードを消せば写真も消えます。
- **外部への接続：** フォント（Google Fonts）だけを外部から読み込みます。接続できないときは標準フォントで表示されます。
- **記憶する値：** コード文字、前に付けるアドレス、最後に開いたタブがブラウザのストレージ（localStorage）に残ります。写真やコードは保存しません。
- **対応ブラウザ：** 最近のバージョンの Chrome、Edge、Safari、Firefox。スマートフォンでも使えます。

### ほかのアドレスで開いた場合

このページは `g.yeon.at` でしか動きません。

- リポジトリをコピーしてほかのアドレス（例：`ユーザー名.github.io`）に置くと、写真の作成も表示も止まり、案内文と g.yeon.at へ移動するボタンだけが表示されます。
- アドレスにコードが付いていた場合、ボタンがそのコードを g.yeon.at に引き継ぐので、受け取った写真はそこで見られます。
- 自分のパソコンでファイルとして開いた場合や `localhost` で開いた場合は、テスト用に動きます。

### 内部の仕組み

```
写真 → 64〜512ピクセルのグリッド → YCbCr → 画像全体の2D DCT → 量子化 → 算術符号化 → ハングルまたは英字
```

1. **縮小：** 写真を長辺64ピクセルのグリッドに縮めます。64ピクセルでは文字が余るほど制限に余裕があれば、96、128、192、256、384、512ピクセルのグリッドを順に試し、元画像に近いほうを選びます。半分ずつ何度か縮めてジャギーを防ぎ、透明な部分は白で塗ります。
2. **色を分ける：** 明るさ（Y）1つと色差（Cb、Cr）2つに分けます。人の目は明るさに敏感なので、色はより粗く扱います。
3. **周波数に変える：** JPEG のような8×8ブロックに分けず、画像全体に DCT を1回かけます。ブロックの境目ができず、低い周波数（大きな塊）から順に記録されます。
4. **量子化：** 周波数が高いほど、また色成分ほど粗く丸めます。圧縮段階（0〜127）が丸めの間隔を決めます。
5. **算術符号化：** 「この値は0か」「1より大きいか」のような問いに分け、それまでの値をもとに確率を変えながら圧縮します（LZMA 方式のレンジコーダー）。
6. **文字にする：** バイト列を13ビットずつハングル音節に、または6ビットずつ英数字にします。
7. **文字数に合わせる：** 上限に収まる最も細かい圧縮段階を二分探索で探します。そのあと、末尾の文字を消しても同じように復元できる限り消し続けます。
8. **復元：** 受け取る側はコサインの波を画面の解像度で直接足し合わせて描きます。グリッドの大きさの画像を引き伸ばすわけではないので、大きく表示してもピクセルの段差がなく、滑らかにぼやけます。

コードの先頭（64ピクセルのグリッドでは62ビット、ハングル約5字）には、バージョン、グリッドの大きさ、縦横比、圧縮段階、平均色、係数の数が入っています。ビット単位の形式とパラメータは [img-dev の詳細ドキュメント](https://github.com/Velvitty/img-dev/blob/main/README.ja.md#コーデックの構造) にあります。

### 制約

- **画質：** ぼやけたプレビュー程度です。文字や細かい模様は判別できません。
- **波紋：** 明るさが急に変わる境目の周りに波紋が出ます。周波数を切り捨てたためです。
- **上限：** グリッドは最大512ピクセルなので、約1万字を超えると文字数を増やしてもほとんど鮮明になりません。
- **時間：** 文字数制限が7,000字以上だと、圧縮に数秒かかります。
- **縦横比：** 約3.8:1より細長い写真はその比率に押しつぶされます。
- **透明度：** 透明な部分は白になります。
- **アニメーションGIF：** 最初のコマだけが入ります。
- **版の違い：** 圧縮のパラメータが変わった版では、以前のコードが違う画像に復元されることがあります。
- **DCInside の自動リンク：** DCInside が `?` の後ろのハングルまでリンクに含めるかは、まだ実際に確認していません。リンクが切れる場合は、英字コードを使うか、受け取った人にコードを表示タブへ貼り付けてもらってください。

### PSNRの読み方

PSNR（ピーク信号対雑音比）は、結果が元画像にどれだけ近いかを dB で表した値です。

`PSNR = 10 × log10(255² ÷ 平均二乗誤差)`

| PSNR | 印象 |
|---|---|
| ∞ | 元画像と完全に同じ |
| 45dB以上 | 目ではほぼ区別できない |
| 35〜40dB | 一般的なJPG程度 |
| 30dB前後 | よく見るとつぶれが見える |
| 25dB前後 | ぼやけているが何かはわかる（ハングルコードの平均） |
| 20dB前後 | 形と色だけが残る |

- 元画像と完全に同じなら誤差が0なので、PSNRは無限大です。
- 誤差が10倍になると、ちょうど10dB下がります。
- この文書の数値は、写真を160×120に縮めて比べた値です。もっと大きくして比べると低くなります。

### トラブルシューティング

| 症状 | 対処 |
|---|---|
| 「이 글자로는 사진을 만들 수 없습니다」（この文字列から写真を作れません） | コードが途切れたか、別の文字が混ざっています。行全体をもう一度コピーしてください。 |
| リンクを開くと作成タブが出て写真がない | コメントの自動リンクが途中で切れた可能性があります。コメントのコードをコピーして表示タブに貼り付けてください。送る側は英字コードを使うと確実です。 |
| コピーボタンが効かない | 文字列が選択された状態なので、Ctrl/⌘+C を押してください。 |
| 写真が元とまったく違って見える | 別の版のページで作ったコードかもしれません。作ったときと同じ版のページで開いてください。 |
| 全体の文字数が上限より少し短い | 正常です。圧縮段階が階段状なので、数文字余ることがあります。 |
| ページが404になる | リポジトリの Pages 設定、ルートの `CNAME` ファイル、DNS の CNAME（`g` → `velvitty.github.io`）を確認してください。最初の設定後は反映まで数分かかります。 |

### よくある質問

**コードから元の写真を復元できますか？**
できません。コードにはぼやけたプレビュー程度の情報しか入っていません。

**同じ写真なら、いつも同じコードになりますか？**
同じブラウザならそうです。ブラウザごとに画像の縮小方法が少し違うため、コードが少し変わることがあります。ただし、一度作ったコードはどのブラウザで開いても同じ写真に復元されます。

**400字より多く書ける場所では？**
文字数制限を増やすとグリッドが大きくなり、鮮明になります（最大512ピクセル）。JPG data リンクタブは、`data:` リンクを画像として表示する場所で使ってください。

**なぜハングルコードは英字コードより鮮明なのですか？**
同じ文字数に約2.2倍の情報が入るからです。英字1文字は64通り、ハングル1文字は8,192通りのうちの1つです。

**ハングルコードが変な文字に見えます。**
`뗈`、`쯿` のようにめったに使わない音節も混ざっているためです。意図的に意味のない文字を使っていて、ほとんどのフォントにすべて含まれています。

### 実装論考

以下の論考は、[Velvitty/img-dev](https://github.com/Velvitty/img-dev) の詳細ドキュメントの各章に載せたものと同じ内容です。コードのパス（`src/`、`lab/`、`build.py`）は img-dev を基準にしています。

#### 実装論考：問題設定

- **何を:** コメント1行（400字）に収まる非可逆画像形式と、それを作成・復元するブラウザページです。
- **なぜ:** DCInside のコメントは400字制限があり、画像を添付できず、`data:` リンクも画像として表示しません（ユーザー確認と以前のセッションでの実測）。写真を送るには、写真そのものを文字で書き表すしかありません。
- **どのように（方法・技術）:** 変換符号化（DCT）→ 量子化 → コンテキスト適応型二値算術符号化 → 文字変換という古典的な非可逆圧縮の流れを、数百バイトという極端に小さい予算に合わせて設計し直しました。
- **数学的アプローチ:** 1文字が運べる情報量は `log2(文字集合の大きさ)` です。base64url は `log2 64 = 6` ビット、使っているハングル音節8,192字は `log2 8192 = 13` ビットです。アドレス19字を除いた381字 × 13ビット = 4,953ビット ≈ 619バイトが、写真に使えるすべてです。シャノンの情報源符号化定理[7]により平均符号長はモデルのエントロピーより短くできないので、写真を低いエントロピーで表すモデル（変換＋コンテキストモデル）と、そのエントロピーにほぼ届く符号器（算術符号）の両方が必要です。
- **工学的アプローチ:** サーバーなしで静的ファイル1つで動き、コード自体がデータのすべてでなければなりません（自己完結）。そのため保存先、アップロード、アカウントはありません。
- **そうした理由（代替案との比較）:** （1）画像ホスティングへのリンクは短いものの、アップロードとサーバーの寿命に依存するため「アップロードなし」の要件に合いません。（2）JPEG の `data:` リンクは量子化表とハフマン表のヘッダーだけで約600バイトあり、base64 で800字を超えます[3][4][26]。（3）BlurHash[35]・ThumbHash[36] は数十字のプレースホルダー向けで成分数が固定されている（BlurHash は縦横それぞれ最大9）ため、400字の予算を使い切れません。そこで、予算に応じて品質が上がる専用コーデックを作りました。
- **価値:** サーバー費用もプライバシーのリスクもなく、文字列さえコピーされれば、どこでもいつまでも同じ写真に復元されます。
- **限界:** 情報量の上限がはっきりしているため、ぼやけたプレビューを超えられません。DCInside がハングルを含むリンクを最後まで自動リンクにするかは、まだ確認していません。
- **参照:** [3], [4], [7], [26], [35], [36]

#### 実装論考：アドレスと転送

- **何を:** `https://g.yeon.at/?コード` 形式のリンクと、長いコードで `#` に切り替える規則です。
- **なぜ:** DCInside のコメントは `https://` で始まらないとクリックできるリンクになりません（ユーザー確認）。コードを `?` の後ろに置くと GitHub Pages はその部分を無視して同じ `index.html` を返すので、サーバー設定なしでアドレスごとに違う写真を開けます。
- **どのように（方法・技術）:** ページは開いたときに `location.search`、なければ `location.hash` を読んでコードを取り出します。コピー時に、URLエンコードしたアドレス全体が7,000バイトを超えると `?` を `#` に変えます。
- **数学的アプローチ:** ハングル音節は UTF-8 で3バイト、アドレスでは1バイトが `%XX` の3文字になるので、1音節は9バイトです。381字のコードは 381 × 9 = 3,429バイト＋アドレス19バイトです。基準の7,000バイトは `(7000 − 19) / 9 ≈ 775` 音節に当たります。
- **工学的アプローチ:** URI の文法[27]では、`?` 以降（クエリ）はサーバーに送られ、`#` 以降（フラグメント）はブラウザに残ります。HTTP では長すぎる要求対象に414を返せます[28]。g.yeon.at に実際に送ると6,000バイトは200、9,000バイトは414だったので（2026-10-26測定）、要求行のほかの部分を見込んで7,000バイトで区切りました。
- **そうした理由（代替案との比較）:** 常に `#` を使えば414の心配はありませんが、ユーザーが望んだ形は `?` で、短いリンクなら `?` でも問題ありません。そこで短ければ `?`、長ければ `#` に分けました。
- **価値:** 400字のリンクはユーザーが望んだ形のままで、数千字のリンクもエラーなく開きます。`#` 以降はサーバーのログにも残りません。
- **限界:** 414の境界は GitHub Pages（前段のCDN）の現在の動作を測った値なので、変わる可能性があります。メッセンジャーや掲示板の自動リンクが非ASCII文字をどこまで含めるかはサービスごとに違います。
- **参照:** [27], [28], [32]

#### 実装論考：静的ホスティング

- **何を:** GitHub Pages に `index.html` と `CNAME` だけを置き、独自ドメイン `g.yeon.at` を付ける公開方法です。
- **なぜ:** 圧縮も復元もブラウザで行うので、サーバーの仕事はファイルを渡すことだけです。
- **どのように（方法・技術）:** img-dev の `build.py` で作った `dist/` を img リポジトリにコピーし、`main` にプッシュします。DNS は `g` の CNAME → `velvitty.github.io` で、証明書は GitHub が Let's Encrypt で発行します[32][33]。
- **工学的アプローチ:** 開発資料（img-dev）と公開版（img）をリポジトリで分け、公開用リポジトリにはユーザーに見せるファイルだけを置きます。アカウントのメールが非公開設定なので、コミットには GitHub の noreply アドレスを使わないとプッシュが受け付けられません[34]。
- **そうした理由（代替案との比較）:** サーバーレス関数や自前のサーバーを置けば、アドレス制限や利用統計をサーバー側で扱えますが、費用と個人情報の取り扱いの負担が生まれます。静的ホスティングが要件に最も単純に合います。
- **価値:** 運用費用がなく、障害点は GitHub Pages だけです。
- **限界:** HTTPS 証明書の発行は GitHub 側の都合で進むため、最初は Enforce HTTPS をすぐにはオンにできません。サーバーコードがないので、アドレス制限のような確認はブラウザ内でしかできません。
- **参照:** [32], [33], [34]

#### 実装論考：前処理

- **何を:** 写真をグリッドの大きさに縮め、白い背景に合成し、YCbCr に変換する段階です。
- **なぜ:** 変換の大きさを予算に合わせて計算量を抑え、明るさと色を分けて色をより粗く扱うためです。
- **どのように（方法・技術）:** キャンバス上で目標の2〜4倍になるまで半分ずつ縮め、最後にグリッドの大きさで描きます。縦横比は `a = round(16 · log2(幅/高さ))` として6ビットに入れます。色変換は JFIF のフルレンジ BT.601 係数（`Y = 0.299R + 0.587G + 0.114B` など）を使います[5][6]。
- **数学的アプローチ:** 標本化定理[38]によれば、k倍の縮小は元の解像度で `1/(2k)` より高い周波数を折り返して混ぜ込みます（エイリアシング）。ブラウザの双線形補間は近傍2×2しか見ないので、一度に大きく縮めると実質的に点サンプリングになります。半分ずつ縮めると各段階が2×2平均に近くなり、ミップマップのピラミッド[18]と同じローパス効果が得られます。比率コードは1オクターブあたり16段階なので比率の誤差は最大 `2^(1/32) ≈ 2.2%`、±31段階で `2^(31/16) ≈ 3.83:1` までです。
- **工学的アプローチ:** 64ピクセルのグリッドはチャンネルあたり 64 × 48 = 3,072 係数で、400字の予算（約619バイト）で実際に0でない数百個を入れるには十分であり、変換は1ミリ秒以内です。人の目は明るさのコントラストより色のコントラストに鈍感なので[17]、色チャンネルを分けておくと量子化で差をつけられます。
- **そうした理由（代替案との比較）:** RGB のまま圧縮すると3チャンネルに同じ情報が重なってビットを無駄にします。4:2:0 のように色を空間的に間引く代わりに、同じグリッドで色チャンネルの間隔を1.7倍にしました。画像全体の DCT では高周波の色係数はどのみち0になるので効果は似ており、実装が単純です。
- **価値:** どんな大きさの写真も同じ経路で扱え、縮小の段差が結果に混ざりません。
- **限界:** ブラウザによってキャンバスの縮小結果が少しずつ違うため、同じ写真でもブラウザによってコードが変わることがあります。3.8:1より細長い写真は押しつぶされます。透明度は白で失われます。
- **参照:** [5], [6], [17], [18], [30], [38]

#### 実装論考：変換

- **何を:** グリッド全体に1回かける2次元 DCT-II と、係数を周波数順に並べる規則です。
- **なぜ:** 自然画像は隣り合う画素どうしの相関が大きいので、DCT をかけるとエネルギーが少数の低周波係数に集まります。残りを0にしても目に見える損失は小さくなります。
- **どのように（方法・技術）:** 分離可能な形で横方向、縦方向の順に計算します。係数は `r = √((u·s/W)² + (v·s/H)²)`、`s = √(W·H)` の小さい順に並べます。
- **数学的アプローチ:** 正規化は次のとおりです。こうすると `A[0,0]` が平均の明るさになり、ほかの係数はそのコサイン波の振幅になります。

  ```math
  A[u,v] = \frac{\alpha_u \alpha_v}{WH} \sum_{x=0}^{W-1}\sum_{y=0}^{H-1} f(x,y)\cos\frac{\pi(2x+1)u}{2W}\cos\frac{\pi(2y+1)v}{2H},\quad \alpha_0=1,\ \alpha_{k>0}=2
  ```

  ```math
  f(x,y) = \sum_{u,v} A[u,v]\cos\frac{\pi(2x+1)u}{2W}\cos\frac{\pi(2y+1)v}{2H}
  ```

  DCT は1次マルコフ過程の最適変換（KLT）に近く、エネルギーの集中がよいことが知られています[1][2]。計算量は `O(W·H·(W+H))` で、64 × 48 グリッドで約34万回、512 × 512 で約2.7億回の乗算です。

- **工学的アプローチ:** 並べる基準 r を正方形に換算した周波数にしたのは、横長の写真と縦長の写真で同じ「見える周波数」が同じ順番に来るようにするためです。並べた結果はグリッドの大きさごとに保存して再利用し、r が同じときは整数の v、u で順を決めるので、ブラウザと Node.js で同じ順序になります。
- **そうした理由（代替案との比較）:** JPEG のような8×8ブロックの DCT[3][4] では、予算が小さいとブロックごとに DC だけが残り、碁盤模様が出ます。ブロックに分ける理由である計算量と局所適応は64〜512のグリッドでは大きな問題にならないので、全体変換を選びました。ウェーブレットは同じ予算で輪郭をよりはっきり保てる可能性がありますが、実装とコンテキストモデルが複雑になります。
- **価値:** 低周波だけが残ってもブロックなしで滑らかにぼやける、ごく小さい予算に合った劣化の仕方になります。
- **限界:** 全体変換なので、一部分の細かい模様が画像全体の予算と競合します。切り捨てたコサイン級数は境目付近で約9%のオーバーシュート（ギブズ現象）[19]を生み、波紋が出ます。高速DCT（FFTベース）[24]はまだ使っておらず、512のグリッドは1秒近くかかります。
- **参照:** [1], [2], [3], [4], [19], [24]

#### 実装論考：量子化

- **何を:** 実数の係数を整数の段階に変える規則（間隔、デッドゾーン、周波数と色の重み、グリッド補正）です。
- **なぜ:** 圧縮率の大部分はここで決まります。目立たない成分をより粗く捨てるほど、同じ文字数でよく見えます。
- **どのように（方法・技術）:** `step = 0.0002 · 1.06^q · (1 + 0.11·r) · （色なら1.7）· （バージョン1なら64/長辺）`、`level = sign(x) · ⌊|x|/step + 0.5 − 0.1⌋`、復元は `level · step` です。
- **数学的アプローチ:** DCT の交流係数はおおむねラプラス分布に従うことが知られており[15]、ラプラス情報源には0の周りを広く取るデッドゾーン付き一様量子化がレート歪みの面で有利です[14]。ここで0になるしきい値は `0.6 · step` です。q を指数にしたのは、`1.06^127 ≈ 1,620` 倍の広い範囲を7ビットで均等に分けるためです（1段階あたり間隔6%）。バージョン1の補正は次の関係から来ます。画素ごとの分散が σ² の細かい模様を正規直交DCTで変換すると係数の分散も σ² ですが、ここで使う振幅係数は正規直交係数に `2/√(WH)` を掛けたものなので、標準偏差は `1/√(WH)`、同じ縦横比なら `1/長辺` に比例して小さくなります。そのため間隔に `64/長辺` を掛けると、グリッドが大きくなっても同じ q が同じ相対精度を意味します。
- **工学的アプローチ:** 周波数の重み `(1 + 0.11r)` はコントラスト感度関数[16]を単純な直線で近似したもので、色の1.7倍は色のコントラスト感度が低いこと[17]を反映しています。値はテスト写真のPSNR比較で選びました（[実験の経緯と判断](https://github.com/Velvitty/img-dev/blob/main/README.ja.md#実験の経緯と判断) の4番）。
- **そうした理由（代替案との比較）:** JPEG 式の8×8量子化表はブロックの大きさに縛られており、全体DCTやグリッドの大きさの変化に合いません。復元値を0側に寄せる方法（shrink）はラプラス仮定のもとでは理論上有利ですが、実測では0が最もよかったので使っていません。
- **価値:** q 1つでレートを滑らかに調整できるので、文字数合わせが単純になります。グリッド補正のおかげで、大きな予算でも文字を最後まで使えます。
- **限界:** 重みはPSNRを基準にテスト写真8枚で選んだ値なので、知覚品質として最適とは限りません。バージョン0のDCは明るさ6ビット、色5ビットなので、平均色が最大で約2/255（明るさ）、4/255（色）ずれることがあります。
- **参照:** [14], [15], [16], [17]

#### 実装論考：エントロピー符号化

- **何を:** 量子化した整数列をビットに変える二値算術符号（レンジコーダー）とコンテキストモデルです。
- **なぜ:** 係数の大部分は0で、0になる確率は周波数や近傍によって大きく変わります。この違いを確率に反映してはじめて、エントロピーに近い長さになります。
- **どのように（方法・技術）:** 係数ごとに「0か → 符号 → 1より大きいか → 2より大きいか → 指数ゴロム」の順の二値判定に分け（CABAC と同じ二値化[11][12]）、各判定をコンテキスト（チャンネル、周波数帯、直前2係数が0かどうか）ごとの確率で符号化します。符号器は LZMA SDK のレンジコーダーの構造（32ビットの範囲、キャッシュを使った桁上がり処理）に従いました[9][10]。
- **数学的アプローチ:** 確率 p の事象には `−log2 p` ビットかかり、算術符号は全体の長さをこの合計より数バイト長くするだけです[8]。末尾に残る余分なバイトは [文字数に合わせる](https://github.com/Velvitty/img-dev/blob/main/README.ja.md#文字数に合わせる) の末尾文字の削除で減らします。ハフマン符号は記号ごとに最低1ビットかかるので確率0.95の「0」にも1ビットを使いますが、算術符号なら約0.074ビットです。確率は11ビットの整数で持ち、ビットごとに `p ← p + (2048 − p)/16`（0のとき）または `p ← p − p/16`（1のとき）で更新します。実効的な記憶長が約16ビットの指数移動平均なので、数百バイトしかないストリームでもすぐに適応します。
- **工学的アプローチ:** コンテキストの数は合計216個と小さく保ちました。データが少ないときにコンテキストが多いと、それぞれが学習する前にストリームが終わってしまうからです。ヘッダーも同じ符号器に確率0.5で通すので、別のビット詰めコードなしでちょうど1ビットずつ使います。
- **そうした理由（代替案との比較）:** LZMA の既定値 SHIFT 5（1/32）より 4（1/16）のほうが検証用写真で0.04dBよくなりました。テスト写真でコンテキスト確率の初期値を学習してみましたが、+0.03〜0.07dB にとどまり、表をコードに入れる手間に見合いませんでした。
- **価値:** 同じ情報を固定長符号よりずっと短く書けるので、400字に数百個の係数を入れられます。
- **限界:** 符号ビットはほぼ1ビットそのままかかります。2次元の近傍（上の係数）はコンテキストに使っておらず、コンテキスト混合のような強いモデルも使っていません。ストリームの途中が壊れると、それ以降がすべて壊れます。
- **参照:** [8], [9], [10], [11], [12], [13]

#### 実装論考：ビットストリーム形式

- **何を:** バージョン、グリッド、縦横比、量子化段階、平均色、係数の数を入れたヘッダーと、その後に続く係数列です。
- **なぜ:** 復号器が別の情報なしに、コードだけから同じグリッド、同じ係数順序、同じ間隔を作り直す必要があるからです。
- **どのように（方法・技術）:** バージョン0は62ビット固定のヘッダーです。バージョン1はバージョンビットの後にグリッド番号3ビットを入れ、DC は8ビットずつ、係数の数は `⌈log2(W·H)⌉` ビットずつにします。
- **数学的アプローチ:** 62ビットは400字の予算（約5,200ビット）の1.2%です。係数の数を終端記号（EOB）ではなくヘッダーに書くと、チャンネルあたり固定の10〜16ビットで済み、係数ごとに「ここで終わりか」を問う費用がかかりません。
- **工学的アプローチ:** 64ピクセルのグリッドは今もバージョン0で書くので、形式を拡張した後も、既存のコードと400字のコードは1ビットも変わっていません（テスト写真の16個のコードで確認）。グリッド番号7は空けてあり、次の形式拡張の印に使えます。
- **そうした理由（代替案との比較）:** バージョンフィールドを最初から複数ビットにしておくほうがきれいでしたが、400字では1ビットも惜しいので1ビットで始め、拡張はバージョン1内の空き値で扱います。
- **価値:** 予算が小さいときのオーバーヘッドを最小に保ちながら、形式を広げる余地を残しました。
- **限界:** チェックサムがないため、途切れたり書き換わったりしたコードを確実には見分けられず、別の画像に復元されることがあります。
- **参照:** [11]

#### 実装論考：文字への変換

- **何を:** バイト列をハングル音節（13ビット）または base64url の文字（6ビット）で書く方法です。
- **なぜ:** コメントは文字数で制限されるので、1文字にできるだけ多くのビットを載せる必要があります。
- **どのように（方法・技術）:** ビット列を13ビットずつ区切って `U+AC00 + 値` で、または6ビットずつ区切って base64url のアルファベット[25]で書きます。読むときは範囲外の文字を無視します。
- **数学的アプローチ:** Unicode のハングル音節は `U+AC00〜U+D7A3` の11,172字です[29]。すべて使えば `log2 11172 ≈ 13.447` ビットで13ビットより3.4%多くなりますが、そのためにはコード全体を1つの大きな数として基数変換する必要があり、計算が `O(n²)` になります。2のべき乗の8,192字だけを使えば、ビットをそのまま切ってつなげるだけで済みます。
- **工学的アプローチ:** 最後の文字の余ったビットは0で埋めます。これは復号器が足りないバイトを0として読む規則とかみ合い、末尾の文字の削除を可能にします。
- **そうした理由（代替案との比較）:** base83（BlurHash[35]）や base85 は6ビットより少し多く載せられますが、`#`、`%`、`?` のようなアドレスの特殊文字を含みます。絵文字や漢字はさらに多くのビットを載せられますが、表示と入力が不安定です。ハングルは DCInside の利用者にとって自然で、ほとんどのフォントに入っています。
- **価値:** 同じ400字に英字の約2.2倍の情報を入れられます。
- **限界:** UTF-8 のバイト数で数える場所では、ハングルは1バイトあたり4.33ビットで英字（6ビット）より不利です。ハングル音節を字母に分解する正規化（NFD）[29]を通るとコードが壊れます。今の復号器は貼り付けた文字列を NFC に戻していません。
- **参照:** [25], [29], [35]

#### 実装論考：レート制御とグリッドの選択

- **何を:** 文字数制限の中で、最も細かい q と最も適したグリッドの大きさを選ぶ方法です。
- **なぜ:** ユーザーは「何字」だけを決め、その中で品質が最大になることを期待します。
- **どのように（方法・技術）:** q を0〜127で二分探索します（7〜8回の符号化）。末尾の文字を1つずつ消してみて、復号結果が同じなら消し続けます。64ピクセルのグリッドが q = 0 でも予算を使い切れないときは、次のグリッドで符号化し直し、2つの結果を大きいほうのグリッドで元画像との平均二乗誤差で比べて、よいほうを残します。
- **数学的アプローチ:** 符号長 R(q) は q に対してほぼ単調に減るので、二分探索で `R(q) ≤ 予算` を満たす最小の q を `⌈log2 128⌉ = 7` 回前後で見つけます。同じレートで解像度を上げて量子化を粗くするか、解像度を下げて量子化を細かくするかは、レート歪み最適化の典型的な問題で[20]、ここでは「小さいグリッドが飽和したときだけ大きいグリッドを試す」貪欲な規則と、実際の誤差の比較で解いています。
- **工学的アプローチ:** q = 0 で収まるグリッドは二分探索をせずにすぐ次へ進むようにして、7,000字の符号化を約1.8秒から1.4秒に縮めました。末尾の文字の削除はレンジコーダーが最後に出す余分なバイトを取り除くもので、実際に復号して確かめるので間違うことはありません。
- **そうした理由（代替案との比較）:** すべてのグリッドを符号化して比べれば、よりよい解が見つかるかもしれませんが、大きいグリッドは1つに数秒かかります。768ピクセルのグリッドも試しましたが、2万字で16秒かかったので外しました。
- **価値:** 400字ではこれまでどおり速く、7,000字では6,968字を使って28.0dBまで上がります。
- **限界:** R(q) が厳密には単調でないため、上限より数文字余ることがあります。貪欲な規則なので最適なグリッドは保証されません。計算はメインスレッドで動くので、大きな予算では画面が少し止まります（Web Worker は未使用）。
- **参照:** [8], [20]

#### 実装論考：復元と拡大

- **何を:** 係数から画面の大きさの画像を直接計算する方法です。
- **なぜ:** グリッドの大きさの画像を作ってから引き伸ばすと、ピクセルの段差や補間のぼやけが重なります。
- **どのように（方法・技術）:** 逆変換の式の x、y に、画面座標をグリッド単位に直した実数を入れて、コサイン級数をそのまま計算します。横方向を先に計算し、係数がすべて0の行は飛ばします。
- **数学的アプローチ:** 逆DCTの式は x が整数でなくても定義される滑らかな関数なので、それを好きな解像度でサンプリングするのは、コサイン基底での帯域制限補間です。計算量は `O(H·W·outW + 行数·outH·outW)` です。
- **工学的アプローチ:** 同じ関数がカードのプレビュー（長辺480px）と表示タブ（960px）の両方を描きます。最後に YCbCr → RGB に変換し、0〜255に切り詰めます。
- **そうした理由（代替案との比較）:** グリッドの大きさで逆DCTをしてからキャンバスの画像補間で引き伸ばせば速くなりますが、小さいグリッドでは双線形補間特有のぼやけた十字模様が見えます。
- **価値:** ごくわずかな情報からでも、見やすい「滑らかにぼやけた」結果が得られます。
- **限界:** ギブズの波紋[19]は拡大してもそのまま見えます。`Math.cos` は仕様上、実装による近似なので[31]、ブラウザによって画素値が±1程度違うことがあります。
- **参照:** [19], [31]

#### 実装論考：ページの設計

- **何を:** 1つのHTMLファイルの中の画面、コードの検出、アドレス制限、設定の記憶です。
- **なぜ:** ユーザーの好み（HTML 1ファイルに JS・CSS を入れ、ブラウザだけで動かす）と、受け取った人が何の準備もなく開けなければならないという条件のためです。
- **どのように（方法・技術）:** コーデックのソースはビルド時にページにそのまま入れます。貼り付けた文章から最も長いハングルの連なり（4字以上）、なければ最後の `?`・`#` の後ろで最も長い base64url の連なりをコードとみなします。アドレスが g.yeon.at・localhost・ファイル・claude.ai のプレビューでなければ、案内だけを描いて処理を止めます。
- **工学的アプローチ:** localStorage が使えなくても既定値で動くよう、すべてのアクセスを例外処理しました。コピーは Clipboard API が拒否されたら文字列を選択しておく方式に切り替えます。キャンバスと画像の処理は HTML 標準の動作（アニメーション画像は既定のフレームを描く）に従います[30]。
- **そうした理由（代替案との比較）:** フレームワークを使えば画面のコードは短くなりますが、ファイルが大きくなり外部依存が生まれます。アドレス制限はサーバーで行えば確実ですが、静的ホスティングにはサーバーコードがありません。
- **価値:** ファイル1つをコピーすれば公開が終わり、オフラインでも動きます（フォントを除く）。
- **限界:** コードの検出はヒューリスティックなので、ハングルのコードより長いハングルの文が混ざると誤認することがあります。アドレス制限はソースを書き換える人を止められない抑止策にすぎません。
- **参照:** [27], [30]

#### 実装論考：ビルド

- **何を:** `src/` のコーデックとページを合わせて、公開版とプレビューを作るスクリプトです。
- **なぜ:** Node.js のテストとブラウザが同じコーデックファイルを使ってこそ、テストしたものと公開したものが同じだと言えます。
- **どのように（方法・技術）:** `src/codec.js` から `module.exports` の行だけを除き、`/*CODEC*/` の位置に入れます。
- **工学的アプローチ:** ビルド結果（`dist/`、`build/`）もリポジトリに入れて、ビルドツールがない場所でも公開版をすぐ使えるようにしました。
- **そうした理由（代替案との比較）:** バンドラー（webpack など）はこの規模には重く、出力にランタイムのコードが混ざります。
- **価値:** 依存関係のない Python 30行でビルドが再現できます。
- **限界:** ビルド結果をコミットするので、ソースと結果がずれないよう、毎回ビルドしてから一緒にコミットする必要があります。

#### 実装論考：評価方法

- **何を:** 画質を数値で比べる方法（PSNR）と、テスト写真、ブラウザテストです。
- **なぜ:** パラメータを選び、変更が以前の結果を壊していないかを確かめるには、再現できる数値が必要です。
- **どのように（方法・技術）:** 元画像を160×120にボックス縮小したものと、復元結果を160×120で描いたものを比べます。大きいグリッドのテストは512×512で比べました。テスト写真は picsum.photos（Unsplash の写真）から取った学習用8枚、検証用6枚です[37]。
- **数学的アプローチ:** 元画像の高周波はどのみち伝えられないので、受け取る側が見る大きさの近くで比べてこそ、コーデックの違いが表れます。PSNR は平均二乗誤差の対数なので、計算が単純で再現しやすい指標です。
- **工学的アプローチ:** コーデックを変えるたびに、400字の結果（平均PSNRとコード文字列）が以前と同じかを確かめて下位互換を守りました。ブラウザテストは Playwright で実際のページを開き、作成、リンクを開く、貼り付け、アドレス制限を確認します。
- **そうした理由（代替案との比較）:** SSIM のような知覚指標のほうが人の判断に近いのですが[21]、ここでは単純で解釈しやすいPSNRから始めました。
- **価値:** 変更で画質が上がったか、既存のコードを壊していないかを数秒で確かめられます。
- **限界:** 写真14枚は小さな標本で、PSNRは知覚品質と食い違うことがあります[21][22]。ユーザーから提供されたテスト画像はリポジトリに入れていません。
- **参照:** [21], [22], [37]

#### 実装論考：PSNRの数学

- **何を:** PSNR の定義と、4ピクセルの例の場合の数の計算です。
- **なぜ:** 「元画像と同じなら何dBか」のような問いに正確に答え、この文書の数値を読む基準を示すためです。
- **どのように（方法・技術）:** 4ピクセル（赤・黄・青・緑）の画像のチャンネル値はすべて0か255なので、もう一方の画像のチャンネル値を0〜255で選ぶと、チャンネルごとの差 d は0〜255で一様になります。誤差二乗和の分布は、d² の分布を12回畳み込んだものです。
- **数学的アプローチ:** `PSNR = 10·log10(255² / MSE)` なので、MSE が10倍になるとちょうど10dB下がり、MSE = 0 なら定義上無限大です。1チャンネルだけ1違うと `MSE = 1/12`、`PSNR = 10·log10(12 · 255²) ≈ 58.9dB` です。場合の数の計算では、FFT による畳み込み[24]の相対誤差が約10⁻¹⁶なので10⁻²⁰より小さい裾の確率が消え、`np.histogram` は累積和の差で区間の値を求めるため、1に近い数から小さな数を引く桁落ち[23]が起きていました。正の数だけを足す直接の畳み込みと `np.bincount` に変えて、58.9dB までの裾を正確に得ました。
- **工学的アプローチ:** PSNR の印象の表は、このプロジェクトで使う経験的な目安であり、文献の標準値ではありません。
- **価値:** 数値の意味を誤解なく伝え、計算誤差でできた偽の棒を正しました。
- **限界:** PSNR は人が感じる品質と食い違うことがあります[21][22]。
- **参照:** [21], [22], [23], [24]
