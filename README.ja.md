# 400字画像圧縮ツール

写真を **コメント1行（400字以内）** に収まる文字列に変換するツールです。DCInsideのコメントのように文字数が短く、画像を投稿できない場所で写真をやり取りするために使います。受け取った人はその文字列をこのページに貼り付けるか、リンクを開いて写真を見ます。

- `index.html` 1ファイルで動作し、すべての処理はブラウザ内で完結します。サーバーもアップロードもありません。
- 結果はぼやけたプレビュー程度です。400字に入る情報は300〜650バイトしかないため、形・色・雰囲気がわかる程度に圧縮されます。

## 使い方

1. **만들기（作成）** タブに写真をドラッグするか、クリックして選ぶか、Ctrl/⌘+V で貼り付けます。
2. **복사（コピー）** を押すと、`https://g.yeon.at/?뗈앏괟샡…` のような400字以内の1行がコピーされます。そのままコメントに貼り付けます。
3. 受け取った人はその行をブラウザのアドレスバーに貼り付ければ、すぐに写真が見られます。**보기（表示）** タブに貼り付けても構いません。前後に別の文章が混ざっていてもコード部分だけを読み取ります。

`https://g.yeon.at/?コード` と `https://g.yeon.at/index.html?コード` のどちらでも動きます。

## 設定

| 項目 | 説明 |
|---|---|
| コード文字：ハングル | 1文字に13ビット。アドレスを付けるとコードに381字、約619バイト入ります。最も鮮明です。 |
| コード文字：英字 | 英数字と `-`・`_` のみで、1文字に6ビット。ハングルが使えない場所向けです。 |
| 前に付けるアドレス | 既定値は `https://g.yeon.at/?`（19字）。`https://` で始めることでコメント内でクリックできるリンクになります。この分だけ写真に使える文字が減ります。空にするとコードだけを出力します。 |
| 文字数制限 | 既定値は400（DCInsideのコメント）です。 |

## 仕組み

1. 写真を長辺64ピクセルのグリッドに縮小し、YCbCr色空間に変換します。文字数に余裕があればグリッドを96〜512ピクセルに広げます。
2. 画像全体に2次元DCTをかけ、低い周波数から順に並べます。
3. 高い周波数ほど、また色（色差）成分ほど粗く量子化します。
4. 結果をコンテキスト適応型の二値算術符号化（LZMA式レンジコーダー）で圧縮します。
5. 文字数制限に収まる最も細かい量子化段階を二分探索で見つけ、復号結果が変わらない限り末尾の文字を削ります。
6. 表示側はコサイン級数を画面解像度で直接計算するため、拡大してもブロック状にならず滑らかです。

## JPG data リンクタブ

`data:` リンクをそのまま画像として表示する場所（HTMLやMarkdownの画像を使える場所）では、通常のJPGを `data:` リンクにして使えます。同じ文字数なら、このページのコードのほうが鮮明です（1200×1200の絵を7,000字で：JPG 25.6dB、ハングルコード 28.0dB）。JPGはファイルヘッダーだけで数百字あるため、400字には収まりません。

## 補足

- DCInside のコメントは画像や `data:` リンクを表示しないため、受け取った人がこのページを直接開く必要があります。
- ハングルコードは `가`（U+AC00）から始まる8,192個の完成形ハングル音節を使います。文字数ではなくバイト数で制限するサイトでは英字コードを使ってください。

### 概要

DCInside のコメントは400字までしか書けず、画像を投稿できず、`data:` リンクも画像として表示しません。通常のJPGを `data:` リンクにすると、ファイルヘッダーだけで約800字になるため、400字には入りません。

このページは、写真を約300〜620バイトに縮める専用の圧縮方式を使います。その結果をハングル音節か英数字で書き表してコメント1行に収め、受け取った人はリンクを開くかコードを貼り付けて写真を見ます。

- アドレス：https://g.yeon.at/
- このリポジトリには公開用ファイル（`index.html`、`CNAME`、README）だけがあります。ソースとテスト資料は [Velvitty/img-dev](https://github.com/Velvitty/img-dev) にあります。

### 画面構成

ページにはタブが3つあります。

#### 作成（만들기）

1. 写真をドラッグするか、枠をクリックして選ぶか、Ctrl/⌘+V で貼り付けます。複数枚まとめて入れられます。
2. 写真ごとにカードができます。左が元画像、右が受け取った人に見える写真です。
3. カード下の数字の意味は次のとおりです。

   | 表示 | 意味 |
   |---|---|
   | 원본（元画像） | 元のファイルサイズ |
   | 코드（コード） | 写真を入れた文字数（アドレスを除く） |
   | 전체（全体） | アドレスを含む文字数と上限。上限内なら緑色です。 |
   | 압축 단계（圧縮段階） | 0〜127。小さいほど細かく圧縮されています。 |
   | 격자（グリッド） | 写真を記録した大きさ。400字なら64px、文字数が多いほど大きくなります（最大512px）。 |

4. ボタンは3つです。
   - **복사（コピー）：** アドレスとコードを1行でコピーします。コピーが使えない環境では文字列を選択しておくので、Ctrl/⌘+C を押してください。
   - **보기 탭에서 확인（表示タブで確認）：** 受け取る側の画面を確認します。
   - **삭제（削除）：** カードを消します。

設定（コード文字、文字数制限、前に付けるアドレス）を変えると、入れてある写真がすべて圧縮し直されます。最初に開くと夕焼けの例が1枚入っていて、`예시（例）` の印が付きます。

#### 表示（보기）

受け取ったコードやリンクを貼り付けると写真が表示されます。

- 前後に別の文章が混ざっていてもコード部分だけを読み取ります。ハングルコードは4字以上続く最も長い部分、英字コードは最後の `?` か `#` の後ろで最も長い部分を選びます。
- 写真の下に、コードの文字数、コードの種類、圧縮段階が表示されます。
- コードが途切れていたり、コードでない文字列だったりすると、その旨を表示します。

リンク（`https://g.yeon.at/?コード`）から来ると、このタブがすぐに開きます。

#### JPG data リンク

文字数制限に余裕がある場所で使うツールです。写真をJPGで圧縮し直し、`data:image/jpeg;base64,…` リンクにします。

| 設定 | 説明 |
|---|---|
| 目標リンク長 | 長さに収まる最も高い品質を探します。品質が35を下回りそうなときだけ画像を縮小します。YouTube・Reddit（9,900）、Instagram（2,150）、GitHub（65,000）のボタンがあり、囲むタグのために少し余裕を残した値です。 |
| 品質指定 | 選んだ品質（5〜95）で1回だけ圧縮します。 |
| 長辺の最大サイズ | 元のまま、1920、1280、800、480ピクセルから選びます。 |

結果はリンク、`<img>` タグ、Markdown 形式でコピーできます。

### コードとリンクの形式

| 形式 | 例 | コードに使える文字 | 入る量 |
|---|---|---|---|
| ハングル + アドレス（既定） | `https://g.yeon.at/?뗈앏괟…` | 381字 | 約619バイト |
| 英字 + アドレス | `https://g.yeon.at/?TqVTweO…` | 381字 | 約285バイト |
| ハングルコードのみ | `뗈앏괟…` | 400字 | 650バイト |
| 英字コードのみ | `TqVTweO…` | 400字 | 300バイト |

- **ハングルコード：** 1文字に13ビット入り、英字の約2.2倍です。`가`（U+AC00）から `쯿`（U+CBFF）までの8,192字を使います。
- **英字コード：** `A–Z a–z 0–9 - _` だけを使います。ハングルが使えない場所や、文字数をバイトで数える場所で使います。
- **`https://` を付ける理由：** DCInside のコメントは `https://` で始まらないとクリックできるリンクになりません。
- **アドレス内のハングル：** アドレスバーにはハングルで表示されますが、ブラウザは1音節を `%EB%97%88` のような9文字にして送ります。381音節で約3.4KBになり、URL長の上限よりずっと短いです。
- **`#` 形式：** `https://g.yeon.at/#コード` でも開きます。アドレスが約7KBを超えるほどコードが長い場合（ハングルで約770字以上）、コピー時に自動で `?` の代わりに `#` を使います。`?` 以降はサーバーに送られ、GitHub Pages は8KBを超えるアドレスを拒否するためです（414エラー）。

### 画質と文字数

写真8枚を `https://g.yeon.at/?` の後ろの381字に圧縮して測った結果です。PSNRは元画像にどれだけ近いかを表す値で、高いほど元画像に近くなります（[PSNRの読み方](#psnrの読み方) を参照）。

| 写真 | 英字コード | ハングルコード |
|---|---|---|
| ベッドの上のパグ | 25.8 dB | 28.0 dB |
| 霧の山と人 | 26.5 dB | 27.6 dB |
| 野原の人 | 24.7 dB | 26.7 dB |
| クマ | 24.2 dB | 26.3 dB |
| セイウチ | 22.6 dB | 23.9 dB |
| 毛布にくるまったパグ（森） | 21.9 dB | 23.1 dB |
| フィヨルドと崖 | 21.1 dB | 22.4 dB |
| 木の床の上の黒い子犬 | 20.8 dB | 22.0 dB |
| **平均** | **23.4 dB** | **25.0 dB** |

向いている写真と向いていない写真がはっきり分かれます。

- **向いている写真：** 大きな塊となめらかな色の変化が中心の写真です。霧、空、近くで撮った顔や動物などです。
- **向いていない写真：** 木目、草むら、岩のように細かい模様が画面いっぱいに広がる写真です。模様に文字を使い切ってもぼやけたままです。
- **先に切り抜く：** 見せたい部分だけを残すと、同じ文字数でずっと鮮明になります。
- **文字：** 400字では文字は読めません。
- **文字数制限を増やすと：** 写真を入れるグリッドが大きくなり、より鮮明になります。1200×1200の絵を512×512で測ると、400字は64pxのグリッドで21.6dB、1,367字は96pxで24.0dB、4,000字は192pxで26.6dB、7,000字は384pxで28.0dBでした。グリッドは最大512pxなので、約1万字を超えるとほとんど良くなりません。

### プライバシーと動作環境

- **アップロードなし：** 写真はブラウザの外に出ません。圧縮も復元もページ内のスクリプトが行います。
- **コードが写真そのもの：** サーバーには何も保存されないので、コードを持っている人なら誰でも同じ写真を見られます。コードを消せば写真も消えます。
- **外部への接続：** フォント（Google Fonts）だけを外部から読み込みます。接続できないときは標準フォントで表示されます。
- **記憶する値：** コード文字、前に付けるアドレス、最後に開いたタブがブラウザのストレージ（localStorage）に残ります。写真やコードは保存しません。
- **対応ブラウザ：** 最近のバージョンの Chrome、Edge、Safari、Firefox。スマートフォンでも使えます。

### ほかのアドレスで開いた場合

このページは `g.yeon.at` でしか動きません。

- リポジトリをコピーしてほかのアドレス（例：`ユーザー名.github.io`）に置くと、写真の作成も表示も止まり、案内文と g.yeon.at へ移動するボタンだけが表示されます。
- アドレスにコードが付いていた場合、ボタンがそのコードを g.yeon.at に引き継ぐので、受け取った写真はそこで見られます。
- 自分のパソコンでファイルとして開いた場合や `localhost` で開いた場合は、テスト用に動きます。

### 内部の仕組み

```
写真 → 64〜512ピクセルのグリッド → YCbCr → 画像全体の2D DCT → 量子化 → 算術符号化 → ハングルまたは英字
```

1. **縮小：** 写真を長辺64ピクセルのグリッドに縮めます。64ピクセルでは文字が余るほど制限に余裕があれば、96、128、192、256、384、512ピクセルのグリッドを順に試し、元画像に近いほうを選びます。半分ずつ何度か縮めてジャギーを防ぎ、透明な部分は白で塗ります。
2. **色を分ける：** 明るさ（Y）1つと色差（Cb、Cr）2つに分けます。人の目は明るさに敏感なので、色はより粗く扱います。
3. **周波数に変える：** JPEG のような8×8ブロックに分けず、画像全体に DCT を1回かけます。ブロックの境目ができず、低い周波数（大きな塊）から順に記録されます。
4. **量子化：** 周波数が高いほど、また色成分ほど粗く丸めます。圧縮段階（0〜127）が丸めの間隔を決めます。
5. **算術符号化：** 「この値は0か」「1より大きいか」のような問いに分け、それまでの値をもとに確率を変えながら圧縮します（LZMA 方式のレンジコーダー）。
6. **文字にする：** バイト列を13ビットずつハングル音節に、または6ビットずつ英数字にします。
7. **文字数に合わせる：** 上限に収まる最も細かい圧縮段階を二分探索で探します。そのあと、末尾の文字を消しても同じように復元できる限り消し続けます。
8. **復元：** 受け取る側はコサインの波を画面の解像度で直接足し合わせて描きます。グリッドの大きさの画像を引き伸ばすわけではないので、大きく表示してもピクセルの段差がなく、滑らかにぼやけます。

コードの先頭（64ピクセルのグリッドでは62ビット、ハングル約5字）には、バージョン、グリッドの大きさ、縦横比、圧縮段階、平均色、係数の数が入っています。ビット単位の形式とパラメータは [img-dev の詳細ドキュメント](https://github.com/Velvitty/img-dev/blob/main/README.ja.md#コーデックの構造) にあります。

### 制約

- **画質：** ぼやけたプレビュー程度です。文字や細かい模様は判別できません。
- **波紋：** 明るさが急に変わる境目の周りに波紋が出ます。周波数を切り捨てたためです。
- **上限：** グリッドは最大512ピクセルなので、約1万字を超えると文字数を増やしてもほとんど鮮明になりません。
- **時間：** 文字数制限が7,000字以上だと、圧縮に数秒かかります。
- **縦横比：** 約3.8:1より細長い写真はその比率に押しつぶされます。
- **透明度：** 透明な部分は白になります。
- **アニメーションGIF：** 最初のコマだけが入ります。
- **版の違い：** 圧縮のパラメータが変わった版では、以前のコードが違う画像に復元されることがあります。
- **DCInside の自動リンク：** DCInside が `?` の後ろのハングルまでリンクに含めるかは、まだ実際に確認していません。リンクが切れる場合は、英字コードを使うか、受け取った人にコードを表示タブへ貼り付けてもらってください。

### PSNRの読み方

PSNR（ピーク信号対雑音比）は、結果が元画像にどれだけ近いかを dB で表した値です。

`PSNR = 10 × log10(255² ÷ 平均二乗誤差)`

| PSNR | 印象 |
|---|---|
| ∞ | 元画像と完全に同じ |
| 45dB以上 | 目ではほぼ区別できない |
| 35〜40dB | 一般的なJPG程度 |
| 30dB前後 | よく見るとつぶれが見える |
| 25dB前後 | ぼやけているが何かはわかる（ハングルコードの平均） |
| 20dB前後 | 形と色だけが残る |

- 元画像と完全に同じなら誤差が0なので、PSNRは無限大です。
- 誤差が10倍になると、ちょうど10dB下がります。
- この文書の数値は、写真を160×120に縮めて比べた値です。もっと大きくして比べると低くなります。

### トラブルシューティング

| 症状 | 対処 |
|---|---|
| 「이 글자로는 사진을 만들 수 없습니다」（この文字列から写真を作れません） | コードが途切れたか、別の文字が混ざっています。行全体をもう一度コピーしてください。 |
| リンクを開くと作成タブが出て写真がない | コメントの自動リンクが途中で切れた可能性があります。コメントのコードをコピーして表示タブに貼り付けてください。送る側は英字コードを使うと確実です。 |
| コピーボタンが効かない | 文字列が選択された状態なので、Ctrl/⌘+C を押してください。 |
| 写真が元とまったく違って見える | 別の版のページで作ったコードかもしれません。作ったときと同じ版のページで開いてください。 |
| 全体の文字数が上限より少し短い | 正常です。圧縮段階が階段状なので、数文字余ることがあります。 |

### よくある質問

**コードから元の写真を復元できますか？**
できません。コードにはぼやけたプレビュー程度の情報しか入っていません。

**同じ写真なら、いつも同じコードになりますか？**
同じブラウザならそうです。ブラウザごとに画像の縮小方法が少し違うため、コードが少し変わることがあります。ただし、一度作ったコードはどのブラウザで開いても同じ写真に復元されます。

**400字より多く書ける場所では？**
文字数制限を増やすとグリッドが大きくなり、鮮明になります（最大512ピクセル）。JPG data リンクタブは、`data:` リンクを画像として表示する場所で使ってください。

**なぜハングルコードは英字コードより鮮明なのですか？**
同じ文字数に約2.2倍の情報が入るからです。英字1文字は64通り、ハングル1文字は8,192通りのうちの1つです。

**ハングルコードが変な文字に見えます。**
`뗈`、`쯿` のようにめったに使わない音節も混ざっているためです。意図的に意味のない文字を使っていて、ほとんどのフォントにすべて含まれています。

### 開発資料

ソース、ビルドスクリプト、テスト写真とスクリプト、実験記録は [Velvitty/img-dev](https://github.com/Velvitty/img-dev) にあります。このリポジトリの `index.html` は、img-dev で `python3 build.py` が作る `dist/` フォルダをコピーしたものです。

### 実装論考

以下の論考は、[Velvitty/img-dev](https://github.com/Velvitty/img-dev) の詳細ドキュメントの各章に載せたものと同じである。コードのパス（`src/`、`lab/`、`build.py`）は img-dev を基準とする。

#### 実装論考：問題設定

DCInside のコメントは400字を超えられず、画像を添付できず、`data:` リンクも画像として表示しない。この条件で写真を伝える方法は、写真そのものを文字で書き表すことしかない。そこでこのプロジェクトでは、コメント1行に収まる非可逆圧縮形式と、それを作成・復元するブラウザページを一緒に設計した。圧縮は変換符号化（DCT）、量子化、コンテキスト適応型二値算術符号化、文字変換と続く古典的な構成に従うが、すべての段階を数百バイトというごく小さい予算に合わせて決め直している。

予算は1文字が運べる情報量から始まる。その量は文字集合の大きさの対数、つまり `log2(文字集合の大きさ)` ビットである。base64url は `log2 64 = 6` ビット、ここで使うハングル音節8,192字は `log2 8192 = 13` ビットを運ぶ。アドレス19字を除いた381字に13ビットずつを掛けると4,953ビット、約619バイトが写真1枚に使えるすべてになる。シャノンの情報源符号化定理[7]によれば、平均符号長はモデルのエントロピーより短くできない。したがって、写真を低いエントロピーで表すモデル（変換とコンテキストモデル）と、そのエントロピーにほぼ届く符号器（算術符号）がそろって初めて、この予算に見分けのつく画像が収まる。

ほかの方法も検討した。画像ホスティングへのリンクは短いが、アップロードとサーバーの寿命に依存するため、サーバーなしでコードだけで完結するという目標に合わない。JPEG を `data:` リンクにすると量子化表とハフマン表だけで約600バイトになり、base64 で800字を超える[3][4][26]。BlurHash[33] と ThumbHash[34] は数十字のプレースホルダー向けで成分数が固定されており（BlurHash は縦横それぞれ最大9）、400字の予算を使い切れない。そこで、予算が増えれば品質も上がる専用コーデックを作った。

この設計によりサーバー費用もプライバシーのリスクもなく、文字列さえコピーされればどこでも同じ写真に復元される。一方で情報量の上限ははっきりしており、400字ではぼやけたプレビューを超えられない。DCInside がハングルを含むリンクを最後まで自動リンクにするかは、まだ確認していない。

#### 実装論考：アドレスと転送

リンクは `https://g.yeon.at/?コード` の形を基本とする。DCInside のコメントは `https://` で始まる文字列だけをクリックできるリンクにし、GitHub Pages は `?` 以降を無視して同じ `index.html` を返す。そのため、サーバーの設定なしにアドレスごとに違う写真を開ける。ページは開いたときに `location.search` を、それが空なら `location.hash` を読んでコードを取り出す。

URI の文法[27]では、`?` 以降のクエリはサーバーに送られ、`#` 以降のフラグメントはブラウザに残る。ハングル音節は UTF-8 で3バイト、アドレスでは1バイトが `%XX` の3文字になるので、1音節は9バイトを占める。381字のコードなら 381 × 9 = 3,429バイトにアドレス19バイトが加わる。HTTP サーバーは長すぎる要求対象に414を返せるが[28]、g.yeon.at に直接送ってみると6,000バイトは受け付け、9,000バイトは414で拒否した。そこで要求行のほかの部分も見込んで、URLエンコード後に7,000バイトを超えるとコピー時に `?` を `#` に変える。この基準は `(7000 − 19) / 9 ≈ 775` 音節に当たる。

常に `#` を使えば414を心配する必要はないが、`?` が基本の形で、短いリンクなら `?` で十分である。そのため400字のリンクは `?` の形のまま使い、数千字のリンクは `#` に切り替わってエラーなく開く。`#` 以降はサーバーの記録にも残らない。ただし414の境界は GitHub Pages とその前段の CDN の現在の動作を測った値なので変わりうるし、掲示板やメッセンジャーの自動リンクが非ASCII文字をどこまでリンクに含めるかはサービスごとに異なる[32]。

#### 実装論考：静的ホスティング

圧縮も復元もブラウザで行うので、サーバーの仕事はファイルを渡すことだけである。そこで GitHub Pages に `index.html` と `CNAME` だけを置き、独自ドメイン `g.yeon.at` を付ける静的ホスティングを選んだ[32]。img-dev の `build.py` で作った `dist/` を img リポジトリにコピーすれば公開は終わる。

開発資料（img-dev）と公開版（img）はリポジトリを分けた。公開用リポジトリにはページに必要なファイルだけを置き、ソースとテスト資料と副産物は開発用リポジトリに集める。サーバーレス関数や自前のサーバーを置けば、アドレス制限や利用統計をサーバー側で扱えるが、費用と個人情報の取り扱いの負担がついてくる。静的ホスティングは運用費用がなく、障害点が GitHub Pages だけという点で、この目標に最も単純に合う。その代わり、アドレス制限のような確認はブラウザ内でしかできない。

#### 実装論考：前処理

前処理は、写真をグリッドの大きさに縮め、白い背景に合成し、YCbCr に変換する段階である。変換の大きさを予算に合わせて計算量を抑え、明るさと色を分けて色をより粗く扱うためだ。色変換には JFIF が使うフルレンジの BT.601 係数（`Y = 0.299R + 0.587G + 0.114B` など）をそのまま使う[5][6]。透明な部分は白で塗る。

縮小には標本化理論の制約がかかる。標本化定理[36]によれば、k倍の縮小は元の解像度で `1/(2k)` より高い周波数を折り返してエイリアシングを生む。ブラウザの双線形補間は近傍2×2の画素しか見ないので、一度に大きく縮めると実質的に点サンプリングになり、この問題を避けられない。そこでキャンバス上で目標の2〜4倍になるまで半分ずつ縮め、最後にグリッドの大きさで描く。各段階が2×2平均に近くなり、ミップマップのピラミッド[18]と同じローパス効果が得られる[30]。

縦横比は `a = round(16 · log2(幅/高さ))` として6ビットに入れる。1オクターブあたり16段階なので比率の誤差は最大 `2^(1/32) ≈ 2.2%` で、±31段階で約3.83:1まで表せる。64ピクセルのグリッドはチャンネルあたり 64 × 48 = 3,072 係数で、400字の予算（約619バイト）で実際に0でない数百個を入れるには十分であり、変換は1ミリ秒以内に終わる。

色を分けておくのは、人の目が明るさのコントラストより色のコントラストに鈍感だからである[17]。RGB のまま圧縮すると、3チャンネルに重なった情報にビットを浪費する。4:2:0 のように色を空間的に間引く代わりに、同じグリッドで色チャンネルの量子化間隔を1.7倍にした。画像全体の DCT では高周波の色係数はどのみち0になるので、効果は似ており実装はより単純である。

こうすれば、どんな大きさの写真も同じ経路で扱え、縮小の段差が結果に混ざらない。ただしブラウザによってキャンバスの縮小結果が少しずつ違うため、同じ写真でもブラウザによってコードが変わることがあり、3.8:1より細長い写真はその比率に押しつぶされ、透明度は白で失われる。

#### 実装論考：変換

自然画像は隣り合う画素どうしの相関が大きい。そのため DCT をかけるとエネルギーが少数の低周波係数に集まり、残りを0にしても目立つ損失は小さい。DCT は1次マルコフ過程の最適変換（KLT）に近く、エネルギーの集中がよいことが知られている[1][2]。このコーデックはグリッド全体に2次元 DCT-II を1回かけ、次のように正規化する。

```math
A[u,v] = \frac{\alpha_u \alpha_v}{WH} \sum_{x=0}^{W-1}\sum_{y=0}^{H-1} f(x,y)\cos\frac{\pi(2x+1)u}{2W}\cos\frac{\pi(2y+1)v}{2H},\quad \alpha_0=1,\ \alpha_{k>0}=2
```

```math
f(x,y) = \sum_{u,v} A[u,v]\cos\frac{\pi(2x+1)u}{2W}\cos\frac{\pi(2y+1)v}{2H}
```

この正規化では `A[0,0]` が平均の明るさになり、ほかの係数はそれぞれのコサイン波の振幅になる。おかげで量子化の間隔を明るさの単位でそのまま決められる。計算は横と縦を順に行う分離可能な形で行い、費用は `O(W·H·(W+H))` である。64 × 48 グリッドで約34万回、512 × 512 グリッドで約2.7億回の乗算になる。

係数は `r = √((u·s/W)² + (v·s/H)²)`、`s = √(W·H)` の小さい順に並べる。正方形に換算した周波数を基準にして、横長の写真と縦長の写真で同じ「見える周波数」が同じ順番に来るようにした。並べた結果はグリッドの大きさごとに保存して再利用し、r が同じときは整数の v、u で順を決めるので、ブラウザと Node.js で同じ順序になる。

JPEG のように8×8ブロックに分けないのには理由がある[3][4]。予算が小さいとブロックごとに DC だけが残り、碁盤模様が出る。ブロックに分ける本来の理由である計算量と局所適応は、64〜512のグリッドでは大きな問題にならない。ウェーブレットは同じ予算で輪郭をよりはっきり保てるが、実装とコンテキストモデルが複雑になる。画像全体の DCT は低周波だけが残ってもブロックなしで滑らかにぼやけるので、ごく小さい予算に合った劣化の仕方をする。

その代わり、全体変換なので一部分の細かい模様が画像全体の予算と競合する。切り捨てたコサイン級数は境目付近で約9%のオーバーシュート（ギブズ現象）[19]を生み、波紋を残す。高速DCT（FFTベース）[24]はまだ使っておらず、512のグリッドは1秒近くかかる。

#### 実装論考：量子化

圧縮率の大部分は量子化で決まる。目立たない成分を粗く捨てるほど、同じ文字数でよく見える。このコーデックの量子化間隔と整数化の規則は次のとおりである。

```math
\mathrm{step} = 0.0002 \cdot 1.06^{q} \cdot (1 + 0.11\,r) \cdot c_{\mathrm{chroma}} \cdot s_{\mathrm{grid}},\qquad \mathrm{level} = \mathrm{sign}(x)\left\lfloor \frac{|x|}{\mathrm{step}} + 0.5 - 0.1 \right\rfloor
```

ここで色チャンネルは `c = 1.7`、バージョン1（96ピクセル以上のグリッド）は `s = 64/長辺` で、復元は `level · step` である。

DCT の交流係数はおおむねラプラス分布に従うことが知られており[15]、ラプラス情報源には0の周りを広く取るデッドゾーン付き一様量子化がレート歪みの面で有利である[14]。上の式で係数が0になるしきい値は `0.6 · step` だ。周波数の重み `1 + 0.11r` はコントラスト感度関数[16]を単純な直線で近似したもので、色の1.7倍は色のコントラスト感度が低いこと[17]を反映している。値はテスト写真のPSNRを比べて選んだ（[実験の経緯と判断](https://github.com/Velvitty/img-dev/blob/main/README.ja.md#実験の経緯と判断) の4番）。q を指数にしたのは、`1.06^127 ≈ 1,620` 倍に及ぶ広い範囲を7ビットで均等に分けるためである。1段階ごとに間隔が6%ずつ変わるのでレートを滑らかに調整でき、文字数合わせが単純になる。

グリッド補正 `s = 64/長辺` は次の関係から来る。画素ごとの分散が σ² の細かい模様を正規直交 DCT で変換すると、係数の分散も σ² になる。ところがここで使う振幅係数は正規直交係数に `2/√(WH)` を掛けた値なので、標準偏差は `1/√(WH)`、同じ縦横比なら `1/長辺` に比例して小さくなる。間隔に `64/長辺` を掛けて初めて、グリッドが大きくなっても同じ q が同じ相対精度を意味する。この補正がないと大きなグリッドでも細かい模様が0に丸められ、256ピクセルのグリッドが1,749字から増えなかった。

JPEG 式の8×8量子化表はブロックの大きさに縛られており、全体 DCT や変わるグリッドに合わない。復元値を0側に寄せる方法はラプラス仮定のもとでは理論上有利だが、実測では寄せないほうが最もよかった。重みはPSNRを基準にテスト写真8枚で選んだ値なので、知覚品質の最適とは異なりうる。バージョン0の DC は明るさ6ビット、色5ビットなので平均色が最大で約2/255（明るさ）、4/255（色）ずれることがあり、バージョン1ではこれを8ビットに増やした。

#### 実装論考：エントロピー符号化

量子化した係数の大部分は0で、0になる確率は周波数や近傍によって大きく変わる。この違いを確率に反映して初めて、エントロピーに近い長さになる。そのため整数列をそのままビットにせず、コンテキストごとの確率を使う二値算術符号で書く。

確率 p の事象には `−log2 p` ビットかかり、算術符号は全体の長さをこの合計より数バイト長くするだけである[8]。ハフマン符号は記号ごとに最低1ビットを使うので確率0.95の「0」にも1ビットを費やすが、算術符号なら約0.074ビットで済む。末尾に残る余分なバイトは [文字数に合わせる](https://github.com/Velvitty/img-dev/blob/main/README.ja.md#文字数に合わせる) の末尾文字の削除で減らす。

係数1つは「0か、符号、1より大きいか、2より大きいか、指数ゴロム」の順の二値判定に分けられる。H.264 の CABAC と同じ二値化である[11][12][13]。各判定は、チャンネル、周波数帯、直前2係数が0かどうかで決まるコンテキストの確率で符号化される。符号器は LZMA SDK のレンジコーダーの構造、つまり32ビットの範囲とキャッシュバイトを使った桁上がり処理に従った[9][10]。

確率は11ビットの整数で持ち、ビットごとに0なら `p ← p + (2048 − p)/16`、1なら `p ← p − p/16` で更新する。実効的な記憶長が約16ビットの指数移動平均なので、数百バイトしかないストリームでもすぐに適応する。LZMA の既定値1/32より1/16のほうが検証用写真で0.04dBよかった。コンテキストは合計216個と小さく保った。データが少ないときにコンテキストが多いと、それぞれが学ぶ前にストリームが終わってしまうからである。テスト写真でコンテキスト確率の初期値を学習してもみたが、0.03〜0.07dBしか得られず、表をコードに入れる負担に見合わなかった。ヘッダーも同じ符号器に確率0.5で通し、別のビット詰めコードなしでちょうど1ビットずつ使う。

こうして書けば同じ情報を固定長符号よりずっと短く表せ、400字に数百個の係数が入る。残る弱点もある。符号ビットはほぼ1ビットそのままかかり、上の係数のような2次元の近傍をコンテキストに使っておらず、コンテキスト混合のような強いモデルも使っていない。ストリームの途中が壊れると、それ以降がすべて壊れる。

#### 実装論考：ビットストリーム形式

復号器はコードだけを見て、同じグリッド、同じ係数順序、同じ間隔を作り直さなければならない。そのためコードの先頭に、バージョン、グリッド、縦横比、圧縮段階、平均色、係数の数を入れたヘッダーを置き、その後に係数列を続ける。

バージョン0のヘッダーは62ビットで、400字の予算（約5,200ビット）の1.2%にあたる。係数の数を終端記号（EOB）ではなくヘッダーに書けば、チャンネルあたり固定の10〜16ビットで済み、係数ごとに「ここで終わりか」を問う費用がかからない[11]。バージョン1はバージョンビットの後にグリッド番号3ビットを入れ、DC を8ビットずつ、係数の数を `⌈log2(W·H)⌉` ビットずつ書く。

形式を広げるときに最も気を配ったのは下位互換である。64ピクセルのグリッドは今もバージョン0で書くので、すでに広まったコードと400字のコードは、形式を広げた後も1ビットも変わっていない（テスト写真の16個のコードで確認）。バージョンフィールドを最初から複数ビットにしておくほうがきれいだったが、400字では1ビットも惜しいので1ビットで始めた。今は0と1の両方を使っているので、次の拡張はバージョン1の空いているグリッド番号7を拡張の印として使う形になる。チェックサムがないため、途切れたり書き換わったりしたコードを確実には見分けられず、別の画像に復元されうる点は残る限界である。

#### 実装論考：文字への変換

コメントは文字数で制限されるので、1文字にできるだけ多くのビットを載せなければならない。そこでバイト列をビットにつなげ、13ビットずつ区切って `U+AC00 + 値` のハングル音節で書くか、6ビットずつ区切って base64url の文字で書く[25]。読むときは範囲外の文字を無視する。

Unicode のハングル音節は `U+AC00〜U+D7A3` の11,172字である[29]。すべて使えば `log2 11172 ≈ 13.447` ビットで、13ビットより3.4%多く載せられる。しかしそのためにはコード全体を1つの大きな数として基数変換する必要があり、計算が `O(n²)` になる。2のべき乗である8,192字だけを使えば、ビットをそのまま切ってつなげればよい。最後の文字の余ったビットは0で埋める。これは復号器が足りないバイトを0として読む規則とかみ合い、末尾の文字の削除を可能にする。

ほかの文字集合も検討した。base83（BlurHash[33]）や base85 は6ビットより少し多く載せられるが、`#`、`%`、`?` のようなアドレスの特殊文字を含む。絵文字や漢字はさらに多くのビットを載せられるが、表示と入力が不安定である。ハングルは DCInside のコメントで自然に使え、ほとんどのフォントに含まれ、同じ400字に英字の約2.2倍の情報を入れられる。

ただし UTF-8 のバイト数で数える場所では、ハングルは1バイトあたり4.33ビットで英字の6ビットより不利である。またハングル音節を字母に分解する正規化（NFD）[29]を通るとコードが壊れるが、今の復号器は貼り付けた文字列を NFC に戻していない。

#### 実装論考：レート制御とグリッドの選択

決めるのは文字数だけで、その中で品質ができるだけ高くなければならない。そのために圧縮段階 q とグリッドの大きさを一緒に選ぶ。

符号長 R(q) は q に対してほぼ単調に減るので、0〜127で二分探索すれば `R(q) ≤ 予算` を満たす最小の q を `⌈log2 128⌉ = 7` 回前後の符号化で見つけられる。次に末尾の文字を1つずつ消してみて、復号結果が変わらなければ消し続ける。レンジコーダーが最後に出す余分なバイトがここでなくなり、実際に復号して確かめるので間違うことはない。

同じレートを解像度に使うか量子化の精度に使うかは、レート歪み最適化の典型的な問題である[20]。ここでは貪欲な規則で解いた。まず64ピクセルのグリッドで圧縮し、q = 0 でも文字が余るなら、そのグリッドでは予算を使い切れないということなので、次の大きさのグリッドで圧縮し直す。2つの結果を大きいほうのグリッドの大きさで元画像との平均二乗誤差で比べてよいほうを残し、大きいグリッドのほうが悪いか q = 0 に届かなくなったら止める[8]。q = 0 で収まるグリッドは二分探索を飛ばすようにして、7,000字の符号化が約1.8秒から1.4秒に縮んだ。

すべてのグリッドを符号化して比べれば、よりよい解が見つかるかもしれないが、大きいグリッドは1つに数秒かかる。768ピクセルのグリッドも試したが、2万字で16秒かかったので外した。結果として400字ではこれまでどおり速く、7,000字では6,968字を使って28.0dBまで上がる。R(q) は厳密には単調でないので上限より数文字余ることがあり、貪欲な規則なので最適なグリッドは保証されず、計算がメインスレッドで動くので大きな予算では画面が少し止まる。

#### 実装論考：復元と拡大

グリッドの大きさの画像を作ってから引き伸ばすと、ピクセルの段差や補間のぼやけが重なる。そこで復号器は、画面の大きさの画像を係数から直接計算する。逆変換の式の x、y に、画面座標をグリッド単位に直した実数を入れ、コサイン級数をそのまま足し合わせる。逆DCTの式は x が整数でなくても定義される滑らかな関数なので、それを好きな解像度でサンプリングすることは、コサイン基底での帯域制限補間になる。

計算は横方向を先に行い、係数がすべて0の行は飛ばす。費用は `O(H·W·outW + 行数·outH·outW)` である。同じ関数がカードのプレビュー（長辺480px）と表示タブ（960px）の両方を描き、最後に YCbCr を RGB に変換して0〜255に切り詰める。グリッドの大きさで逆DCTをしてからキャンバスの補間で引き伸ばせば速くなるが、小さいグリッドでは双線形補間特有のぼやけた十字模様が見える。

この方式はごくわずかな情報からでも、見やすく滑らかにぼやけた結果を作る。ギブズの波紋[19]は拡大してもそのまま残り、`Math.cos` は仕様上、実装による近似なので[31]、ブラウザによって画素値が±1程度違うことがある。

#### 実装論考：ページの設計

ページは、HTML 1ファイルに JS と CSS をすべて入れ、ブラウザだけで動かすという方針で作った。受け取った人が何の準備もなく開けなければならず、公開はファイル1つをコピーするだけで終わるべきだからである。コーデックのソースはビルド時にページにそのまま入り、フォントを除けばオフラインでも動く。フレームワークを使えば画面のコードは短くなるが、ファイルが大きくなり外部依存が生まれる。

貼り付けた文章からコードを探すときは、4字以上続くハングルのうち最も長いものを選び、なければ最後の `?` か `#` の後ろで最も長い base64url の連なりを選ぶ[27]。前後に別の言葉が混ざってもコードだけを読み取れるが、コードより長いハングルの文が混ざると誤って選ぶことがある。

localStorage が使えなくても既定値で動くよう、すべてのアクセスを例外処理した。クリップボード API が拒否されたら、文字列を選択しておく方式に切り替える。キャンバスと画像の処理は HTML 標準の動作に従い、アニメーション画像は既定のフレームを描く[30]。

アドレス制限は、ページが g.yeon.at、localhost、ローカルファイル、claude.ai のプレビュー以外で開かれると、案内だけを描いて処理を止める。確実な制限はサーバーで行うべきだが、静的ホスティングにはサーバーコードがないので、この確認はソースを書き換える人までは止められない抑止策にとどまる。

#### 実装論考：ビルド

Node.js のテストとブラウザが同じコーデックファイルを使ってこそ、テストしたコードと公開したコードが同じだと言える。そのため `build.py` は `src/codec.js` から `module.exports` の行だけを除いて、ページの `/*CODEC*/` の位置に入れる。依存関係のない Python 30行でビルドが再現できる。webpack のようなバンドラーはこの規模には重く、出力にランタイムのコードを混ぜる。ビルド結果（`dist/`、`build/`）もリポジトリに入れて、ビルドツールがない場所でもすぐ使えるようにした。そのぶん、ソースと結果がずれないよう、毎回ビルドしてから一緒にコミットする。

#### 実装論考：評価方法

パラメータを選び、変更が以前の結果を壊していないかを確かめるには、再現できる数値が必要である。このプロジェクトでは、元画像を160×120にボックス縮小した画像と、復元結果を160×120で描いた画像のPSNRを比べる。大きいグリッドのテストは512×512で比べた。元画像の高周波はどのみち伝えられないので、受け取る側が見る大きさの近くで比べて初めてコーデック間の違いが表れる。PSNR は平均二乗誤差の対数なので、計算が単純で再現しやすい。

テスト写真は picsum.photos（Unsplash の写真）から取った学習用8枚と検証用6枚である[35]。コーデックを変えるたびに、400字の結果、つまり平均PSNRとコード文字列が以前と同じかを確かめて下位互換を守った。ブラウザテストは Playwright で実際のページを開き、作成、リンクを開く、貼り付け、アドレス制限を確認する。

SSIM のような知覚指標のほうが人の判断に近いが[21]、単純で解釈しやすいPSNRから始めた。写真14枚は小さな標本で、PSNRは知覚品質と食い違うことがある[21][22]。大きな文字数のテストに使った1200×1200の画像はリポジトリに入れていない。

#### 実装論考：PSNRの数学

PSNR は次のように定義する。

```math
\mathrm{PSNR} = 10 \log_{10} \frac{255^2}{\mathrm{MSE}}
```

したがって MSE が10倍になるとちょうど10dB下がり、MSE が0なら定義上無限大である。4ピクセル（赤・黄・青・緑）の画像で1チャンネルだけ1違うと `MSE = 1/12` なので、`PSNR = 10·log10(12 · 255²) ≈ 58.9dB` になる。

場合の数のグラフは次の観察から出発する。4ピクセルの画像のチャンネル値はすべて0か255なので、もう一方の画像のチャンネル値を0〜255で選ぶと、チャンネルごとの差 d は0〜255で一様になる。誤差二乗和の分布は、d² の分布を12回畳み込んだものである。最初は FFT による畳み込み[24]を使ったが、相対誤差が約10⁻¹⁶なので10⁻²⁰より小さい裾の確率が消えた。また `np.histogram` は累積和の差で区間の値を求めるので、1に近い数からごく小さい数を引く桁落ちが起きた[23]。正の数だけを足す直接の畳み込みと `np.bincount` に変えて、ようやく58.9dBまでの裾を正確に得た。

PSNR の印象の表は、このプロジェクトで使う経験的な目安であり、文献の標準値ではない。PSNR は人が感じる品質と食い違うことがある[21][22]。
