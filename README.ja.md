# 400字画像圧縮ツール

写真をコメント1行に収まる文字列に変え、その文字列をまた写真として表示するウェブページ。

**https://g.yeon.at/**

![元画像と、400字・1,000字・4,000字・7,000字に圧縮した結果](docs/example.jpg)

<sub>左から元画像、400字、1,000字、4,000字、7,000字（ハングルコード、アドレス込み）。写真：Thomas Lefebvre / Unsplash</sub>

DCInside のコメントのように文字数が短く、画像を投稿できない場所で写真をやり取りするために作った。写真はブラウザの中で数百バイトに圧縮されて `https://g.yeon.at/?뗈앏괟…` のような1行になり、受け取った人はそのリンクを開いて写真を見る。

- サーバーも、アップロードも、保存先もない。コードそのものが写真である。
- ハングル音節1文字に13ビットを入れ、同じ文字数に英字の約2.2倍の情報を載せる。
- 文字数制限を増やすと、写真を入れるグリッドが64ピクセルから512ピクセルまで大きくなり、鮮明になる。
- HTML ファイル1つで動く。

## 使い方

ページは **만들기**（作成）、**보기**（表示）、**JPG data 링크**（JPG data リンク）の3つのタブでできている。

### 作成

1. 写真をドラッグするか、枠をクリックして選ぶか、Ctrl/⌘+V で貼り付ける。複数枚まとめて入れられる。
2. 写真ごとにカードができる。左が元画像、右が受け取った人に見える写真である。
3. **복사**（コピー）を押すとアドレスとコードが1行でコピーされる。その行をそのままコメントに貼る。

カードの下には、元のサイズ、コードの文字数、全体の文字数と上限、グリッドの大きさ、圧縮段階（0〜127、小さいほど細かい）が表示される。

| 設定 | 既定値 | 説明 |
|---|---|---|
| コード文字 | ハングル | ハングルは1文字に13ビット、英字は6ビットを入れる。英字はハングルを使えない場所のためのものである。 |
| 文字数制限 | 400 | DCInside のコメント（400）、ツイート（280）、1,000 のボタンがあり、直接入力もできる。 |
| 前に付けるアドレス | `https://g.yeon.at/?` | コードの前に付く文字列。空にするとコードだけを出力する。 |

設定を変えると入れてある写真がすべて圧縮し直され、設定はブラウザに記憶される。

### 表示

受け取ったリンクを開くとこのタブがすぐに開き、写真が表示される。コピーしたコードをこのタブに貼り付けてもよい。前後に別の文章が混ざっていても、コード部分だけを読み取る。

### JPG data リンク

`data:` リンクを画像として表示する場所（HTML や Markdown の画像を使える場所）のための道具である。写真を JPG で圧縮し直して `data:image/jpeg;base64,…` リンクを作る。目標の長さに合わせて品質を探すことも、品質を直接決めることもでき、リンク、`<img>` タグ、Markdown 形式でコピーできる。同じ文字数なら **만들기** タブのコードのほうが鮮明である（[画質](#画質)を参照）。

## コードとリンク

| 形式 | 例 | コードに使う文字 | 入る量 |
|---|---|---|---|
| ハングル + アドレス（既定） | `https://g.yeon.at/?뗈앏괟…` | 381字 | 約619バイト |
| 英字 + アドレス | `https://g.yeon.at/?TqVTweO…` | 381字 | 約285バイト |
| ハングルコードのみ | `뗈앏괟…` | 400字 | 650バイト |
| 英字コードのみ | `TqVTweO…` | 400字 | 300バイト |

- アドレスが `https://` で始まらないと、コメントでクリックできるリンクにならない。
- コードが長くアドレスが約7KBを超える場合（ハングルで約770字以上）、`?` の代わりに `#` を使う。`https://g.yeon.at/#コード` でも同じ写真が開く。
- `https://g.yeon.at/index.html?コード` でも開くが、10字多く使う。

## 画質

文字数制限を増やすと、写真を入れるグリッドが大きくなり鮮明になる。例の画像のクマの写真（1280×960）をハングルコードで圧縮し、640×480で測った結果である。

| 制限 | 実際に使った文字 | グリッド | PSNR | 同じ文字数の JPG `data:` リンク |
|---|---|---|---|---|
| 400 | 387 | 64px | 23.9 dB | 入らない |
| 1,000 | 955 | 96px | 25.5 dB | 入らない |
| 4,000 | 3,810 | 256px | 27.7 dB | 26.2 dB |
| 7,000 | 6,877 | 512px | 28.8 dB | 27.4 dB |
| 10,000 | 8,526 | 512px | 29.2 dB | 28.2 dB |

グリッドは最大512ピクセルなので、この写真は約8,500字を超えると増やしても変わらない。圧縮時間は1,000字までは0.1秒未満、4,000字で約0.4秒、7,000字以上で約3秒である。

400字（アドレス込み）で写真8枚を160×120で測った結果は次のとおりである。

| 写真 | 英字コード | ハングルコード |
|---|---|---|
| ベッドの上のパグ | 25.8 dB | 28.0 dB |
| 霧の山と人 | 26.5 dB | 27.6 dB |
| 野原の人 | 24.7 dB | 26.7 dB |
| クマ | 24.2 dB | 26.3 dB |
| セイウチ | 22.6 dB | 23.9 dB |
| 毛布にくるまったパグ（森） | 21.9 dB | 23.1 dB |
| フィヨルドと崖 | 21.1 dB | 22.4 dB |
| 木の床の上の黒い子犬 | 20.8 dB | 22.0 dB |
| **平均** | **23.4 dB** | **25.0 dB** |

- 大きな塊となめらかな色の変化が中心の写真（霧、空、近くで撮った顔や動物）はよく写る。
- 木目、草むら、岩のように細かい模様が画面を覆う写真は、同じ文字数でよりぼやける。
- 見せたい部分だけを先に切り抜くと、同じ文字数でずっと鮮明になる。
- 400字では文字は読めない。

PSNR は結果が元画像にどれだけ近いかを表す値で、高いほど元画像に近い。以下はこの文書で使う経験的な目安である（[PSNRの数学](#psnrの数学)を参照）。

| PSNR | 印象 |
|---|---|
| ∞ | 元画像と同じ |
| 45 dB 以上 | 目ではほぼ区別できない |
| 35〜40 dB | 一般的な JPG 程度 |
| 30 dB 前後 | よく見るとつぶれが見える |
| 25 dB 前後 | ぼやけているが何かはわかる |
| 20 dB 前後 | 形と色だけが残る |

## プライバシーと動作環境

- 写真はブラウザの外に出ない。圧縮も復元もページ内のスクリプトが行う。
- サーバーには何も保存されないので、コードを持っている人なら誰でも同じ写真を見られる。コードを消せば写真も消える。
- 外部から読み込むのはフォント（Google Fonts）だけで、読み込めないときは標準のフォントで表示される。
- ブラウザのストレージ（localStorage）には、コード文字、前に付けるアドレス、最後に開いたタブだけが残る。写真とコードは保存しない。
- 最近のバージョンの Chrome、Edge、Safari、Firefox で動き、スマートフォンでも使える。
- ページは g.yeon.at でしか動かない。ほかのアドレスに置くと案内と g.yeon.at へのボタンだけが表示され、アドレスにコードがあればそのコードを g.yeon.at に引き継ぐ。

## 制約

- 400字ではぼやけたプレビュー程度で、文字や細かい模様は判別できない。
- 明るさが急に変わる境目の周りに波紋が出る。
- グリッドは最大512ピクセルなので、文字数を増やし続けても一定以上は鮮明にならない。
- 7,000字以上は圧縮に数秒かかり、その間ページが少し止まる。
- 縦横比が約3.8:1より細長い写真はその比率に押しつぶされ、透明な部分は白になり、アニメーション GIF は最初のコマだけが入る。
- UTF-8 のバイト数で文字数を数える場所ではハングルコードが不利なので、英字コードを使う。
- DCInside が `?` の後ろのハングルまで自動リンクにするかは、まだ確認していない。

## トラブルシューティング

| 症状 | 対処 |
|---|---|
| 「이 글자로는 사진을 만들 수 없습니다」（この文字列から写真を作れません） | コードが途切れたか、別の文字が混ざっている。行全体をもう一度コピーする。 |
| リンクを開くと作成タブが出て写真がない | コメントの自動リンクが途中で切れた可能性がある。コメントのコードをコピーして表示タブに貼り付ける。送る側は英字コードを使えばよい。 |
| コピーボタンが効かない | 文字列が選択された状態なので、Ctrl/⌘+C を押す。 |
| 写真が元とまったく違って見える | 圧縮方式が違う版で作ったコードかもしれない。 |
| 全体の文字数が上限より少し短い | 正常である。圧縮段階が階段状なので、数文字余ることがある。 |

## よくある質問

**コードから元の写真を復元できるか？**
できない。コードにはぼやけたプレビュー程度の情報しか入っていない。

**同じ写真なら、いつも同じコードになるか？**
同じブラウザならそうなる。ブラウザごとに画像の縮小方法が少し違うためコードが少し変わることはあるが、一度作ったコードはどのブラウザで開いても同じ写真に復元される。

**なぜハングルコードは英字コードより鮮明なのか？**
同じ文字数に約2.2倍の情報が入るからである。英字1文字は64通り、ハングル1文字は8,192通りのうちの1つである。

**ハングルコードが変な文字に見える。**
`뗈`、`쯿` のようにめったに使わない音節が混ざっているためである。意味のない文字をわざと使っており、ほとんどのフォントにすべて含まれている。

## 実装論考

圧縮は次の順で進む。この章では、各段階をなぜそう作ったのか、どのような数学と工学的判断に基づくのか、何を得て何を諦めたのかを述べる。

```
写真 → グリッドに縮小（64〜512px）→ YCbCr → 画像全体の2D DCT → 量子化 → コンテキスト適応型二値算術符号化 → ハングルまたは英字
```

### 設計目標

DCInside のコメントは400字を超えられず、画像を添付できず、`data:` リンクも画像として表示しない。この条件で写真を伝える方法は、写真そのものを文字で書き表すことしかない。そこで、コメント1行に収まる非可逆圧縮形式と、それを作成・復元するブラウザページを一緒に設計した。圧縮は変換符号化、量子化、エントロピー符号化、文字変換と続く古典的な構成に従うが、すべての段階を数百バイトというごく小さい予算に合わせて決め直している。

予算は1文字が運べる情報量から始まる。その量は `log2(文字集合の大きさ)` ビットである。base64url は `log2 64 = 6` ビット、ここで使うハングル音節8,192字は `log2 8192 = 13` ビットを運ぶ。アドレス19字を除いた381字に13ビットずつを掛けると4,953ビット、約619バイトが写真1枚に使えるすべてになる。シャノンの情報源符号化定理[1]によれば、平均符号長はモデルのエントロピーより短くできない。したがって、写真を低いエントロピーで表すモデル（変換とコンテキストモデル）と、そのエントロピーにほぼ届く符号器（算術符号）がそろって初めて、この予算に見分けのつく画像が収まる。

ほかの方法も検討した。画像ホスティングへのリンクは短いが、アップロードとサーバーの寿命に依存するため、コードだけで完結するという目標に合わない。JPEG を `data:` リンク[2]にすると量子化表とハフマン表だけで約600バイトになり、base64 で800字を超える[3][4]。BlurHash[5] と ThumbHash[6] は数十字のプレースホルダー向けで成分数が固定されており（BlurHash は縦横それぞれ最大9）、400字の予算を使い切れない。そこで、予算が増えれば品質も上がる専用コーデックを作った。

この設計にはサーバー費用もプライバシーのリスクもなく、文字列さえコピーされればどこでも同じ写真に復元される。一方で情報量の上限ははっきりしており、400字ではぼやけたプレビューを超えられない。

### 前処理

前処理は、写真をグリッドの大きさに縮め、白い背景に合成し、YCbCr に変換する段階である。変換の大きさを予算に合わせて計算量を抑え、明るさと色を分けて色をより粗く扱うためだ。色変換には JFIF が使うフルレンジの BT.601 係数（`Y = 0.299R + 0.587G + 0.114B` など）をそのまま使う[7][8]。透明な部分は白で塗る。

縮小には標本化理論の制約がかかる。標本化定理[9]によれば、k倍の縮小は元の解像度で `1/(2k)` より高い周波数を折り返してエイリアシングを生む。ブラウザの双線形補間は近傍2×2の画素しか見ないので、一度に大きく縮めると実質的に点サンプリングになり、この問題を避けられない。そこでキャンバス上で目標の2〜4倍になるまで半分ずつ縮め、最後にグリッドの大きさで描く[10]。各段階が2×2平均に近くなり、ミップマップのピラミッド[11]と同じローパス効果が得られる。

縦横比は `a = round(16 · log2(幅/高さ))` として6ビットに入れる。1オクターブあたり16段階なので比率の誤差は最大 `2^(1/32) ≈ 2.2%` で、±31段階で約3.83:1まで表せる。64ピクセルのグリッドはチャンネルあたり 64 × 48 = 3,072 係数で、400字の予算で実際に0でない数百個を入れるには十分であり、変換は1ミリ秒以内に終わる。

色を分けておくのは、人の目が明るさのコントラストより色のコントラストに鈍感だからである[12]。RGB のまま圧縮すると、3チャンネルに重なった情報にビットを浪費する。4:2:0 のように色を空間的に間引く代わりに、同じグリッドで色チャンネルの量子化間隔を1.7倍にした。画像全体の DCT では高周波の色係数はどのみち0になるので、効果は似ており実装はより単純である。

こうすれば、どんな大きさの写真も同じ経路で扱え、縮小の段差が結果に混ざらない。ただしブラウザによってキャンバスの縮小結果が少しずつ違うため、同じ写真でもブラウザによってコードが変わることがあり、3.8:1より細長い写真はその比率に押しつぶされ、透明度は白で失われる。

### 変換

自然画像は隣り合う画素どうしの相関が大きい。そのため DCT をかけるとエネルギーが少数の低周波係数に集まり、残りを0にしても目立つ損失は小さい。DCT は1次マルコフ過程の最適変換（KLT）に近く、エネルギーの集中がよいことが知られている[13][14]。このコーデックはグリッド全体に2次元 DCT-II を1回かけ、次のように正規化する。

```math
A[u,v] = \frac{\alpha_u \alpha_v}{WH} \sum_{x=0}^{W-1}\sum_{y=0}^{H-1} f(x,y)\cos\frac{\pi(2x+1)u}{2W}\cos\frac{\pi(2y+1)v}{2H},\quad \alpha_0=1,\ \alpha_{k>0}=2
```

```math
f(x,y) = \sum_{u,v} A[u,v]\cos\frac{\pi(2x+1)u}{2W}\cos\frac{\pi(2y+1)v}{2H}
```

この正規化では `A[0,0]` が平均の明るさになり、ほかの係数はそれぞれのコサイン波の振幅になる。おかげで量子化の間隔を明るさの単位でそのまま決められる。計算は横と縦を順に行う分離可能な形で行い、費用は `O(W·H·(W+H))` である。64 × 48 グリッドで約34万回、512 × 512 グリッドで約2.7億回の乗算になる。

係数は `r = √((u·s/W)² + (v·s/H)²)`、`s = √(W·H)` の小さい順に並べる。正方形に換算した周波数を基準にして、横長の写真と縦長の写真で同じ「見える周波数」が同じ順番に来るようにした。並べた結果はグリッドの大きさごとに保存して再利用し、r が同じときは整数の v、u で順を決めるので、ブラウザと Node.js で同じ順序になる。

JPEG のように8×8ブロックに分けないのには理由がある[3]。予算が小さいとブロックごとに DC だけが残り、碁盤模様が出る。ブロックに分ける本来の理由である計算量と局所適応は、64〜512のグリッドでは大きな問題にならない。ウェーブレットは同じ予算で輪郭をよりはっきり保てるが、実装とコンテキストモデルが複雑になる。画像全体の DCT は低周波だけが残ってもブロックなしで滑らかにぼやけるので、ごく小さい予算に合った劣化の仕方をする。

その代わり、全体変換なので一部分の細かい模様が画像全体の予算と競合する。切り捨てたコサイン級数は境目付近で約9%のオーバーシュート（ギブズ現象）[15]を生み、波紋を残す。高速DCT（FFTベース）[16]はまだ使っておらず、512のグリッドでは変換だけで1秒近くかかる。

### 量子化

圧縮率の大部分は量子化で決まる。目立たない成分を粗く捨てるほど、同じ文字数でよく見える。量子化間隔と整数化の規則は次のとおりである。

```math
\mathrm{step} = 0.0002 \cdot 1.06^{q} \cdot (1 + 0.11\,r) \cdot c_{\mathrm{chroma}} \cdot s_{\mathrm{grid}},\qquad \mathrm{level} = \mathrm{sign}(x)\left\lfloor \frac{|x|}{\mathrm{step}} + 0.5 - 0.1 \right\rfloor
```

色チャンネルは `c = 1.7`、96ピクセル以上のグリッドは `s = 64/長辺` で、復元は `level · step` である。

DCT の交流係数はおおむねラプラス分布に従うことが知られており[17]、ラプラス情報源には0の周りを広く取るデッドゾーン付き一様量子化がレート歪みの面で有利である[18]。上の式で係数が0になるしきい値は `0.6 · step` だ。周波数の重み `1 + 0.11r` はコントラスト感度関数[19]を単純な直線で近似したもので、色の1.7倍は色のコントラスト感度が低いこと[12]を反映している。

q を指数にしたのは、`1.06^127 ≈ 1,620` 倍に及ぶ広い範囲を7ビットで均等に分けるためである。1段階ごとに間隔が6%ずつ変わるのでレートを滑らかに調整でき、文字数合わせが単純になる。最初は基準0.004、倍率1.09、6ビットの q で始めたが、最も細かい段階でも360字のうち110〜190字しか使えないほど粗かったので、今の範囲に広げた。

重みの値は、調整用の写真8枚で1つずつ変えながら平均PSNR（英字360字、ハングル360字、英字150字の平均）を比べて選んだ。基準（beta 0.11、chroma 1.7、dz 0.22、shrink 0.08）の平均は23.165dBだった。

| パラメータ | 値と平均PSNR |
|---|---|
| beta（周波数の重み） | 0.05 → 23.183、0.08 → 23.180、0.15 → 23.152、0.2 → 23.106 |
| chroma（色の倍率） | 1.3 → 23.125、2.2 → 23.153、3 → 23.119 |
| dz（デッドゾーン） | 0.1 → 23.253、0.3 → 23.076、0.4 → 22.965 |
| shrink（復元値を0側に寄せる量） | 0 → 23.213、0.15 → 23.102 |

差がはっきりした dz と shrink は0.1と0に変え、差が0.02dB未満の beta と chroma はそのままにした。復元値を0側に寄せる方法はラプラス仮定のもとでは理論上有利だが、実測では寄せないほうが最もよかった。

グリッド補正 `s = 64/長辺` は次の関係から来る。画素ごとの分散が σ² の細かい模様を正規直交 DCT で変換すると、係数の分散も σ² になる。ところがここで使う振幅係数は正規直交係数に `2/√(WH)` を掛けた値なので、標準偏差は `1/√(WH)`、同じ縦横比なら `1/長辺` に比例して小さくなる。間隔に `64/長辺` を掛けて初めて、グリッドが大きくなっても同じ q が同じ相対精度を意味する。補正がないと、大きなグリッドでも細かい模様が0に丸められる。例の画像のクマの写真は、補正なしでは512ピクセルのグリッドまで広げても1,303字（26.1dB）から増えなかったが、補正後は7,000字の制限で6,877字を使って28.8dBになった。

JPEG 式の8×8量子化表はブロックの大きさに縛られており、全体 DCT や変わるグリッドに合わない。重みはPSNRを基準にテスト写真で選んだ値なので、知覚品質の最適とは異なりうる。64ピクセルのグリッドの DC は明るさ6ビット、色5ビットなので平均色が最大で約2/255（明るさ）、4/255（色）ずれることがあり、96ピクセル以上のグリッドではこれを8ビットに増やした。

### エントロピー符号化

量子化した係数の大部分は0で、0になる確率は周波数や近傍によって大きく変わる。この違いを確率に反映して初めて、エントロピーに近い長さになる。そのため整数列をそのままビットにせず、コンテキストごとの確率を使う二値算術符号で書く。

確率 p の事象には `−log2 p` ビットかかり、算術符号は全体の長さをこの合計より数バイト長くするだけである[20]。ハフマン符号は記号ごとに最低1ビットを使うので確率0.95の「0」にも1ビットを費やすが、算術符号なら約0.074ビットで済む。末尾に残る余分なバイトは [レート制御とグリッドの選択](#レート制御とグリッドの選択) の末尾文字の削除で減らす。

係数1つは「0か、符号、1より大きいか、2より大きいか、指数ゴロム」の順の二値判定に分けられる。H.264 の CABAC と同じ二値化である[21][22][23]。各判定は、チャンネル、周波数帯、直前2係数が0かどうかで決まるコンテキストの確率で符号化される。符号器はレンジコーダー[24]を、LZMA SDK の構造、つまり32ビットの範囲とキャッシュバイトを使った桁上がり処理で実装した[25]。

確率は11ビットの整数で持ち、ビットごとに0なら `p ← p + (2048 − p)/16`、1なら `p ← p − p/16` で更新する。実効的な記憶長が約16ビットの指数移動平均なので、数百バイトしかないストリームでもすぐに適応する。検証用写真6枚で更新幅1/8、1/16、1/32の平均PSNRは25.372、25.385、25.344dBで、1/16が最もよかった。コンテキストは合計216個と小さく保った。データが少ないときにコンテキストが多いと、それぞれが学ぶ前にストリームが終わってしまうからである。テスト写真でコンテキスト確率の初期値を学習してもみたが、0.03〜0.07dBしか得られず、表をコードに入れる負担に見合わなかった。ヘッダーも同じ符号器に確率0.5で通し、別のビット詰めコードなしでちょうど1ビットずつ使う。

こうして書けば同じ情報を固定長符号よりずっと短く表せ、400字に数百個の係数が入る。残る弱点もある。符号ビットはほぼ1ビットそのままかかり、上の係数のような2次元の近傍をコンテキストに使っておらず、コンテキスト混合のような強いモデルも使っていない。ストリームの途中が壊れると、それ以降がすべて壊れる。

### ビットストリーム

復号器はコードだけを見て、同じグリッド、同じ係数順序、同じ間隔を作り直さなければならない。そのためコードの先頭にヘッダーを置き、その後に Y、Cb、Cr の順で係数列を続ける。ヘッダーは同じ符号器に確率0.5で入る。64ピクセルのグリッドは形式0で書く。

| フィールド | ビット | 値 |
|---|---|---|
| 形式 | 1 | 0 |
| 比率コード | 6 | a + 32 |
| 圧縮段階 q | 7 | 0〜127 |
| Y DC | 6 | 平均の明るさ × 63 |
| Cb、Cr DC | 5、5 | （平均 + 0.5）× 31 |
| Y、Cb、Cr 係数の数 | 12、10、10 | 0〜4,095、0〜1,023 |

96ピクセル以上のグリッドは形式1で書く。形式ビットの後にグリッド番号3ビット（0〜6がそれぞれ64、96、128、192、256、384、512ピクセル）が続き、DC は8ビットずつ、係数の数は `⌈log2(W·H)⌉` ビットずつである。

形式0のヘッダーは62ビットで、400字の予算（約5,200ビット）の1.2%にあたる。係数の数を終端記号（EOB）ではなくヘッダーに書けば、チャンネルあたり固定の10〜16ビットで済み、係数ごとに「ここで終わりか」を問う費用がかからない[21]。グリッドを広げる形式を加えたときも64ピクセルのグリッドは形式0のまま残したので、すでに広まったコードと400字のコードは1ビットも変わっていない（テスト写真の16個のコードで確認）。形式フィールドを最初から複数ビットにしておくほうがきれいだったが、400字では1ビットも惜しいので1ビットで始めた。今は0と1の両方を使っているので、次の拡張は空いているグリッド番号7を拡張の印として使う。チェックサムがないため、途切れたり書き換わったりしたコードを確実には見分けられず、別の画像に復元されうる点は残る限界である。

### 文字への変換

コメントは文字数で制限されるので、1文字にできるだけ多くのビットを載せなければならない。そこでバイト列をビットにつなげ、13ビットずつ区切って `U+AC00 + 値` のハングル音節で書くか、6ビットずつ区切って base64url の文字で書く[26]。読むときは範囲外の文字を無視する。

Unicode のハングル音節は `U+AC00〜U+D7A3` の11,172字である[27]。すべて使えば `log2 11172 ≈ 13.447` ビットで、13ビットより3.4%多く載せられる。しかしそのためにはコード全体を1つの大きな数として基数変換する必要があり、計算が `O(n²)` になる。2のべき乗である8,192字だけを使えば、ビットをそのまま切ってつなげればよい。最後の文字の余ったビットは0で埋める。これは復号器が足りないバイトを0として読む規則とかみ合い、末尾の文字の削除を可能にする。

ほかの文字集合も検討した。base83（BlurHash[5]）や base85 は6ビットより少し多く載せられるが、`#`、`%`、`?` のようなアドレスの特殊文字を含む。絵文字や漢字はさらに多くのビットを載せられるが、表示と入力が不安定である。ハングルは DCInside のコメントで自然に使え、ほとんどのフォントに含まれ、同じ400字に英字の約2.2倍の情報を入れられる。

ただし UTF-8 のバイト数で数える場所では、ハングルは1バイトあたり4.33ビットで英字の6ビットより不利である。またハングル音節を字母に分解する正規化（NFD）[27]を通るとコードが壊れるが、今の復号器は貼り付けた文字列を NFC に戻していない。

### レート制御とグリッドの選択

決めるのは文字数の上限だけで、その中で品質ができるだけ高くなければならない。そのために圧縮段階 q とグリッドの大きさを一緒に選ぶ。

符号長 R(q) は q に対してほぼ単調に減るので、0〜127で二分探索すれば `R(q) ≤ 予算` を満たす最小の q を `⌈log2 128⌉ = 7` 回前後の符号化で見つけられる。次に末尾の文字を1つずつ消してみて、復号結果が変わらなければ消し続ける。レンジコーダーが最後に出す余分なバイトがここでなくなり、実際に復号して確かめるので間違うことはない[20]。

同じレートを解像度に使うか量子化の精度に使うかは、レート歪み最適化の典型的な問題である[28]。ここでは貪欲な規則で解いた。まず64ピクセルのグリッドで圧縮し、q = 0 でも文字が余るなら、そのグリッドでは予算を使い切れないということなので、次の大きさのグリッドで圧縮し直す。2つの結果を大きいほうのグリッドの大きさで元画像との平均二乗誤差で比べてよいほうを残し、大きいグリッドのほうが悪いか q = 0 に届かなくなったら止める。q = 0 で収まるグリッドは二分探索を飛ばすようにして、クマの写真の7,000字の圧縮が3.5秒から2.9秒に縮んだ。

すべてのグリッドを符号化して比べれば、よりよい解が見つかるかもしれないが、大きいグリッドは1つに数秒かかる。768ピクセルのグリッドも試したところ、クマの写真を2万字の制限で圧縮すると13,003字を使って29.9dBになったが、7.5秒かかった。512ピクセルのグリッドの最大（8,526字、29.2dB、3.2秒）より0.7dB良いだけだったので、512ピクセルまでとした。結果として400字の圧縮は0.01秒で終わり、7,000字では6,877字を使って28.8dBまで上がる（Node.js 22）。R(q) は厳密には単調でないので上限より数文字余ることがあり、貪欲な規則なので最適なグリッドは保証されず、計算がメインスレッドで動くので大きな予算では画面が少し止まる。

### 復元と拡大

グリッドの大きさの画像を作ってから引き伸ばすと、ピクセルの段差や補間のぼやけが重なる。そこで復号器は、画面の大きさの画像を係数から直接計算する。逆変換の式の x、y に、画面座標をグリッド単位に直した実数を入れ、コサイン級数をそのまま足し合わせる。逆DCTの式は x が整数でなくても定義される滑らかな関数なので、それを好きな解像度でサンプリングすることは、コサイン基底での帯域制限補間になる。

計算は横方向を先に行い、係数がすべて0の行は飛ばす。費用は `O(H·W·outW + 行数·outH·outW)` である。同じ関数がカードのプレビュー（長辺480px）と表示タブ（960px）の両方を描き、最後に YCbCr を RGB に変換して0〜255に切り詰める。グリッドの大きさで逆DCTをしてからキャンバスの補間で引き伸ばせば速くなるが、小さいグリッドでは双線形補間特有のぼやけた十字模様が見える。

この方式はごくわずかな情報からでも、見やすく滑らかにぼやけた結果を作る。ギブズの波紋[15]は拡大してもそのまま残り、`Math.cos` は仕様上、実装による近似なので[29]、ブラウザによって画素値が±1程度違うことがある。

### アドレスと転送

リンクは `https://g.yeon.at/?コード` の形を基本とする。DCInside のコメントは `https://` で始まる文字列だけをクリックできるリンクにし、静的ホスティングは `?` 以降を無視して同じ `index.html` を返す。そのため、サーバーの設定なしにアドレスごとに違う写真を開ける。ページは開いたときに `location.search` を、それが空なら `location.hash` を読んでコードを取り出す。

URI の文法[30]では、`?` 以降のクエリはサーバーに送られ、`#` 以降のフラグメントはブラウザに残る。ハングル音節は UTF-8 で3バイト、アドレスでは1バイトが `%XX` の3文字になるので、1音節は9バイトを占める。381字のコードなら 381 × 9 = 3,429バイトにアドレス19バイトが加わる。HTTP サーバーは長すぎる要求対象に414を返せるが[31]、g.yeon.at に直接送ってみると6,000バイトは受け付け、9,000バイトは414で拒否した。そこで要求行のほかの部分も見込んで、URLエンコード後に7,000バイトを超えるとコピー時に `?` を `#` に変える。この基準は `(7000 − 19) / 9 ≈ 775` 音節に当たる。

常に `#` を使えば414を心配する必要はないが、`?` が基本の形で、短いリンクなら `?` で十分である。そのため400字のリンクは `?` の形のまま使い、数千字のリンクは `#` に切り替わってエラーなく開く。`#` 以降はサーバーの記録にも残らない。414の境界は現在のホスティングの動作を測った値なので変わりうるし、掲示板やメッセンジャーの自動リンクが非ASCII文字をどこまでリンクに含めるかはサービスごとに異なる。

### ページの設計

圧縮も復元もブラウザで行うので、サーバーの仕事はファイルを渡すことだけである。そこで GitHub Pages に独自ドメイン `g.yeon.at` を付けた静的ホスティングを選んだ[32]。サーバーレス関数や自前のサーバーを置けば、アドレス制限や利用統計をサーバー側で扱えるが、費用と個人情報の取り扱いの負担がついてくる。静的ホスティングは運用費用がなく、障害点が1つだけである。

ページは HTML 1ファイルに JS と CSS をすべて入れる。受け取った人が何の準備もなく開けなければならず、公開はファイル1つをコピーするだけで終わるべきだからである。コーデックはビルド時にページにそのまま入り、フォントを除けばオフラインでも動く。フレームワークを使えば画面のコードは短くなるが、ファイルが大きくなり外部依存が生まれる。

貼り付けた文章からコードを探すときは、4字以上続くハングルのうち最も長いものを選び、なければ最後の `?` か `#` の後ろで最も長い base64url の連なりを選ぶ[30]。前後に別の言葉が混ざってもコードだけを読み取れるが、コードより長いハングルの文が混ざると誤って選ぶことがある。localStorage が使えなくても既定値で動くよう、すべてのアクセスを例外処理し、クリップボード API が拒否されたら文字列を選択しておく方式に切り替える。キャンバスと画像の処理は HTML 標準に従い、アニメーション画像は既定のフレームを描く[10]。

アドレス制限は、ページが g.yeon.at、localhost、ローカルファイル、プレビュー環境以外で開かれると、案内だけを描いて処理を止める。確実な制限はサーバーで行うべきだが、静的ホスティングにはサーバーコードがないので、この確認はソースを書き換える人までは止められない抑止策にとどまる。

### 画質の評価

パラメータを選び、変更が以前の結果を壊していないかを確かめるには、再現できる数値が必要である。そこで元画像をボックス縮小した画像と、復元結果を同じ大きさで描いた画像のPSNRを比べる。400字の結果は受け取る側が見る大きさに近い160×120で、文字数による変化は640×480で測った。元画像の高周波は400字ではどのみち伝えられないので、見る大きさの近くで比べて初めてコーデック間の違いが表れる。PSNR は平均二乗誤差の対数なので、計算が単純で再現しやすい。

テスト写真は picsum.photos から取った Unsplash の写真で、パラメータの調整に使った8枚と、結果の検証に使った6枚である[33]。コーデックを変えるたびに、400字の結果、つまり平均PSNRとコード文字列が以前と同じかを確かめて下位互換を守った。JPG `data:` リンクとの比較では、Pillow（libjpeg）で大きさと品質を変えながら、文字数に収まる最もよい結果を選んだ。ブラウザテストは Playwright で実際のページを開き、作成、リンクを開く、貼り付け、アドレス制限を確認する。

SSIM のような知覚指標のほうが人の判断に近いが[34]、単純で解釈しやすいPSNRから始めた。写真14枚は小さな標本で、PSNRは知覚品質と食い違うことがある[34][35]。

### PSNRの数学

PSNR は次のように定義する。

```math
\mathrm{PSNR} = 10 \log_{10} \frac{255^2}{\mathrm{MSE}}
```

したがって MSE が10倍になるとちょうど10dB下がり、MSE が0なら定義上無限大である。4ピクセル（赤・黄・青・緑）の画像で1チャンネルだけ1違うと `MSE = 1/12` なので、`PSNR = 10·log10(12 · 255²) ≈ 58.9dB` になる。

4ピクセルの画像で起こりうるすべての場合のPSNR分布は、次の観察から出発する。4ピクセルの画像のチャンネル値はすべて0か255なので、もう一方の画像のチャンネル値を0〜255で選ぶと、チャンネルごとの差 d は0〜255で一様になる。誤差二乗和の分布は、d² の分布を12回畳み込んだものである。最初は FFT による畳み込み[16]を使ったが、相対誤差が約10⁻¹⁶なので10⁻²⁰より小さい裾の確率が消えた。また `np.histogram` は累積和の差で区間の値を求めるので、1に近い数からごく小さい数を引く桁落ちが起きた[36]。正の数だけを足す直接の畳み込みと `np.bincount` に変えて、ようやく58.9dBまでの裾を正確に得た。その結果、でたらめに塗った画像のPSNRの中央値は4.8dBで、完全に同じになるのは約7.9 × 10²⁸通りのうち1通りである。

[画質](#画質)の章のPSNRの印象の表は、このプロジェクトで使う経験的な目安であり、文献の標準値ではない。PSNR は人が感じる品質と食い違うことがある[35]。
